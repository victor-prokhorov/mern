# Job queue

## What this is

An async job queue on plain Postgres: work submitted now, executed later, by one of a fleet of interchangeable workers, with retries, a per-account fairness cap, and a dead-letter path for work that will never succeed. `POST /api/messages` writes the message row and enqueues a `send_message` job in the same transaction (`src/services/messages.js:9-29`); a separate worker process claims jobs, runs a handler by `kind`, and records the outcome. This app was originally scoped as `sql-scheduler` — queue, scheduler, and alerting together — and was narrowed mid-build to the queue alone (see `docs/plan.md`'s scope note); a scheduler deciding *when* recurring work should run is a different, related problem this app deliberately does not solve. **A queue answers "how does this work get done, reliably, eventually"; a scheduler answers "when should it happen."**

## How it works here

**Claiming is one statement, and it mutates state.** `claimJobs` (`src/repositories/jobs.js:19-69`) is the one thing this app shares with `sql-ledger`'s outbox relay — `FOR UPDATE SKIP LOCKED` — and the one place it fundamentally differs. The outbox's claim only reads; nothing is written until delivery is confirmed, so a crashed relay strands nothing. This queue's claim marks rows `running` in the same statement that selects them, which means a crashed worker *does* strand its claimed rows unless something else reclaims them — hence the lease, the reaper, and the fence below. The query itself is a four-CTE pipeline: `locked` takes a candidate pool of due, `ready` rows with `FOR UPDATE OF j SKIP LOCKED` (never plain `FOR UPDATE` — see core concepts); `running_counts` aggregates how many jobs are already `running` per `payload->>'accountId'`; `ranked` window-partitions the locked pool by that same account key; `candidates` keeps only rows whose rank leaves room under `perAccountLimit` once already-running jobs for that account are subtracted, then caps the final result to the caller's `limit`; the outer `UPDATE ... FROM candidates` stamps `status='running'`, `locked_by`, `locked_at` (via `date_trunc('milliseconds', now())` — see below for why), and `lease_expires_at`.

**The inner `LIMIT` is a fairness-versus-contention tradeoff, not a free "generous pool."** `lockLimit` (`src/repositories/jobs.js:20`) decides how many candidate rows the `locked` CTE actually locks before `candidates` narrows them down to `limit`. An earlier version set this to a flat `Math.max(limit * 10, 100)` regardless of whether fairness ranking was even in use, reasoning that "more candidates gives the ranking function more to work with." Measured against four workers each claiming 5 rows from a pool of 100 ready jobs, 20 trials: full batches (`5,5,5,5`) in only 2/20, and at least one worker got 0 of its requested 5 in 8/20 — locking 10-100x the requested row count meant most of those workers spent their `SKIP LOCKED` claim contending over rows the other workers had already locked, rather than partitioning cleanly. The fix ties the headroom to whether fairness is actually requested: `perAccountLimit == null ? limit : limit * 5` — with no per-account cap, there is no ranking computation and therefore no reason to lock more than the `limit` rows this call will actually take; with a cap, the ranking function needs *some* headroom across accounts, but a small proportional multiplier (not a flat floor) is enough. Reran the same probe after the fix: 20/20 trials clean. The lesson generalizes: over-locking to give a downstream filter more to choose from is a real tradeoff against the very throughput `SKIP LOCKED` exists to buy back, and the right amount of headroom is "just enough for the filter that needs it," not "as much as seems safe."

**Lease expiry and the reaper.** `reapExpired` (`src/repositories/jobs.js:71-92`) returns any `running` job whose `lease_expires_at < now()` to `ready` (or straight to `dead` if this reap would exceed `max_attempts`), incrementing `attempts` either way, itself using `FOR UPDATE SKIP LOCKED` so a reaper and a claimer never block each other. It appends `'; lease expired'` to whatever `last_error` a prior `failJob` had already recorded rather than overwriting it, so an operator inspecting a reaped or dead job still sees the real failure reason instead of only the generic "lease expired." `index.js:30-32` runs it on a `setInterval` alongside the worker.

**The fence.** `completeJob`, `failJob`, and `releaseLease` (`src/repositories/jobs.js:105-148`) all match `WHERE id = $1 AND locked_by = $2 AND locked_at = $3 AND status = 'running'`. `locked_by` alone is not enough: the realistic case is the *same* worker id reclaiming its own job after a restart or a garbage-collection pause long enough for its lease to expire, then the original, still-running call finally finishes and tries to complete — same `locked_by`, different epoch. `locked_at` is the fencing token (in the sense of Kleppmann's argument below): each claim stamps a fresh one, so the stale call's write matches zero rows and is a silent no-op rather than corrupting the reclaimer's in-flight job. `test/queue.test.js`'s "the fence" tests deliberately reuse one `workerId` across the stale claim and the reclaim to prove this — see the mutation note under Standard practice.

**Millisecond-truncated timestamps, and a real bug this caught.** `locked_at` is stamped with `date_trunc('milliseconds', now())` (`src/repositories/jobs.js:58`) rather than bare `now()`, because Postgres's `timestamptz` carries microsecond precision but `pg` parses it into a JS `Date`, which only has millisecond precision — comparing a round-tripped `Date` back against a microsecond-precision column in the fence's `locked_at = $3` would silently never match. A related, worse version of the same class of bug shipped and was caught by real (non-flaky-tolerant) test runs during development: `failJob`'s retry path originally computed `nextRunAt` as `new Date(Date.now() + delayMs)` in JavaScript, then compared it against `run_at <= now()` in SQL — mixing the app process's clock with the database's. Under any clock skew between the Node process and the Postgres container, a retry with `delayMs` near zero could compute a `run_at` a few milliseconds *ahead* of the database's own clock, so the very next claim would find no ready rows. It reproduced intermittently in the real test suite (`test/queue.test.js`'s dead-lettering test would occasionally see an empty claim), not as a logic error but as a genuine race between two different clocks. The fix (`src/repositories/jobs.js:128-137`) computes the delay entirely in SQL — `run_at = now() + ($5 * interval '1 millisecond')` — so retry scheduling only ever touches the database's own clock, never the app's.

**Heartbeats.** `runJob` (`src/queue/worker.js:24-49`) starts a `setInterval` heartbeat at `leaseMs / 3` for the duration of the handler call, and clears it in a `finally` no matter how the handler settles. A worker whose process is genuinely alive keeps extending its own lease; a worker whose process has died stops heartbeating with it, and the reaper reclaims the job once the lease actually expires. `leaseMs` has to sit strictly between the slowest healthy job's real running time (too short reaps live work, producing duplicate execution once a handler isn't idempotent) and how long an operator is willing to wait before a genuinely crashed job's work is retried (too long delays every legitimate retry by that same margin).

**Failure, retry, and dead-lettering.** `queue/service.js:25-31`'s `failJob` decides `dead = (attempts + 1) >= maxAttempts` and computes `delayMs` via `backoffMs` (`src/queue/backoff.js:1-4`) — full jitter, `random() * min(cap, base * 2 ** attempts)` — only when it isn't dead. A dead job is excluded from `claimJobs`'s `WHERE status = 'ready'` forever after, so it can never block a healthy job behind it; `POST /api/jobs/:id/retry` (`src/repositories/jobs.js:163-172`) sets `status` back to `ready` and increments `max_attempts` by exactly one — deliberately not resetting `attempts` to zero, which would silently hand the job a whole fresh retry budget rather than the single additional attempt an operator asked for. It also deliberately does not clear `last_error`: a retried job carries its previous failure reason on `GET /api/jobs` until it either fails again (a new `last_error` overwrites it) or succeeds — an operator who retried it can still see what killed it last time while the retry is in flight, rather than the field going blank and looking like it was never touched.

**Idempotent handlers, because delivery is at-least-once.** The registered `send_message` handler (`src/services/messages.js:37-54`) claims `messages.status` `pending`/`sending` → `sending` *before* it ever calls the upstream (`messagesRepo.beginSending`, `src/repositories/messages.js:17-23`) — an earlier version called the guarded write (`markSent`) only *after* the POST, which meant the guard protected the messages row but never protected the actual delivery: a replayed job (the reaper reclaimed it after a slow-but-successful delivery, say) always re-sent the HTTP call regardless of whether the first send had already succeeded. With the claim moved first, a replay that arrives after the message is already `sent` finds `beginSending` matches nothing, returns `false`, and skips the POST entirely — no second send. The handler also catches its own delivery error: if `job.attempts + 1 >= job.max_attempts` — this is the job's last allowed try, the same attempt that will make `failJob` dead-letter it — it calls `messagesRepo.markFailed` before re-throwing, so an operator looking at a permanently-failed message sees `failed`, not a message silently stuck mid-flight forever. (An earlier version of this fix didn't do this: a message whose job dead-lettered stayed `sending` indefinitely, which was actually *worse* than the pre-fix behaviour of staying `pending` — at least `pending` didn't claim to be in flight.) The one honest residual left, deliberately not fixed: `beginSending`'s guard still accepts `sending` (not only `pending`), because a reaped/retried job has to be able to make forward progress if its original attempt is genuinely dead — which means a crash between the POST succeeding and `markSent`'s write leaves the message stuck `sending`, and the next legitimate retry of that job *will* re-POST. That narrow gap is not a bug to chase away; it is exactly why at-least-once delivery requires idempotency at the *receiver*, not just discipline at the sender — see [`mern-shop/server/src/idempotency/README.md`](../../../mern-shop/server/src/idempotency/README.md) for the same conclusion reached from the receiving side, with a fencing token to match.

**Fairness.** The `perAccountLimit` mechanism above stops one account's ten-thousand-message backlog from starving another account's one message: the window function ranks each account's own candidates independently, so account B's single job is never behind nine of account A's in the same claim batch purely because of insertion order. `index.js:13,25` wires this into the running worker as `WORKER_PER_ACCOUNT_LIMIT` (default 5) — it is not merely a parameter the tests happen to exercise; the shipped process runs with a real cap.

**Graceful shutdown.** `worker.stop({ timeoutMs })` (`src/queue/worker.js:72-82`) stops claiming immediately, waits up to `timeoutMs` for in-flight jobs to finish naturally, and for whatever is still in flight past the deadline, calls `releaseLease` — same fence, same columns — so an in-flight job goes back to `ready` immediately rather than sitting `running` with a dead worker's name on it until the reaper eventually notices. `index.js:39-40` wires this to both `SIGTERM` and `SIGINT`. Be precise about what this buys back: `releaseLease` fixes the *bookkeeping* — the row stops lying about who owns it — but it does nothing to the JavaScript call stack still executing the handler inside `runJob`. Nothing here cancels or awaits that in-flight promise; the old process simply exits (`process.exit(0)`) once the lease is released, and whatever the handler does after that point (an in-flight `fetch` that still resolves, for instance) happens in a process about to disappear, disconnected from the row it was working on. A job released this way is picked up and re-run by the next worker to claim it — the fence protects the queue's bookkeeping, not the side effect, which is the same lesson idempotent handlers exist to cover.

## The core concepts

- **A queue is not an outbox.** An outbox's claim never writes (`sql-ledger/src/repositories/outbox.js`'s `claimUnpublished` just reads), so a crashed relay strands nothing — the row is exactly as unclaimed as it always was. A queue's claim has to write `running` somewhere, because "nobody else should also run this" is the entire point, and that write is exactly what a crashed worker leaves behind. Every mechanism in this file — lease, reaper, heartbeat, fence — exists to answer the question an outbox never has to ask: what happens to a claim after its owner disappears mid-work?
- **At-least-once, never exactly-once, and a fence does not change that.** The fence stops a superseded worker's *write* from corrupting the queue's own bookkeeping; it does nothing to stop that worker's *handler* from having already run. If the handler already sent an email before its lease expired, the email was already sent — the fence only guarantees the jobs table itself ends up consistent about who owns what. Exactly-once execution is not a thing this or any at-least-once queue can promise; idempotent handlers are what turns "delivered at least once" into "effectively exactly once" from the outside.
- **`SKIP LOCKED` buys non-blocking, not deduplication — the two properties look identical from a single-worker test and diverge completely under real concurrency.** Plain `FOR UPDATE` also prevents two workers claiming the same row (the second blocks until the first's transaction ends, then sees whatever's left) — that's correct, but it serializes every worker behind whichever one got there first, defeating the entire reason to run more than one. `test/queue.test.js` has a test that holds one row locked in an open, uncommitted transaction from a second connection and asserts a concurrent claim still returns the *other* ready rows in well under 500ms; with plain `FOR UPDATE` substituted in, that same test hangs until mocha's timeout, and — worse — the *next* test's `beforeEach` truncate hangs behind the same held lock too, wedging the entire remaining suite. That cascading wedge is the real-world shape of the bug: a naive claim doesn't just fail one worker's request, it can back up every worker behind one stuck transaction.
- **Fencing tokens: the general pattern behind `locked_at`.** Martin Kleppmann's argument (below) is that a lease alone cannot distinguish "the holder is dead" from "the holder is just paused" — a client can believe it still holds a lock well after its lease has technically expired (a GC pause, a scheduling delay, a slow disk), and a second client that legitimately reclaims the same resource now has two owners who both believe they're exclusive. The fix is a monotonically increasing number handed out with every acquisition, checked by whatever the holder writes to next, so a stale write is rejected rather than silently applied. `locked_at` plays that exact role here: it isn't just "when did we claim this" for logging, it's the token a superseded write is checked against.
- **Backoff needs jitter, or "exponential" alone just delays the collision.** `base * 2 ** attempts` alone makes every job that failed at the same moment retry at the same moment again — same collision, later. Full jitter (`random() * capped`) spreads that same population across the whole delay window instead of concentrating it at one edge. AWS's own simulations (below) are specific about how strong this claim is: full jitter clearly beats *equal* jitter (which does slightly more work and takes longer), but full jitter versus *decorrelated* jitter is "less clear" — both are reasonable choices, and this queue's choice of full jitter is not a claim that it's strictly superior to every alternative.
- **Dead-lettering is what stops a poison job from costing anything.** A job whose handler will never succeed (a permanently malformed payload, a permanently-gone recipient) would otherwise cost one wasted claim-and-fail cycle forever. Once `attempts >= max_attempts`, `failJob` moves it to `dead` and `claimJobs`'s `WHERE status = 'ready'` excludes it from every future claim — it costs nothing further, and it can never block a healthy job behind it in the same `ORDER BY priority DESC, run_at ASC, id ASC` because it's no longer a candidate at all.
- **Priority inversion and starvation are the same failure at two different scopes.** Without the fairness ranking, one account's backlog starves another account's job at the *tenant* scope; without an `ORDER BY priority DESC`, a flood of low-priority work starves high-priority work at the *job* scope. This app addresses both with mechanisms in the same claim statement rather than a second pass, because a second pass would have to re-derive exactly the same snapshot the first pass already locked.
- **When Postgres is enough, and when it stops being enough.** This queue is genuinely production-viable at moderate volume — the SKIP LOCKED pattern is exactly what several real Postgres-backed queue libraries (`pgqueuer`, `pg-boss`, Sidekiq's newer Postgres modes) use under the hood. It stops being enough once you need cross-database routing, consumer groups with independent offsets into a shared log, exactly-once semantics a broker can approximate via transactional producers, or claim throughput high enough that `FOR UPDATE SKIP LOCKED`'s row-level locking becomes the bottleneck rather than the fix. The honest failure mode in practice is not that Postgres becomes technically insufficient — it's that most teams reach for SQS, Redis, or Kafka *long* before their actual volume needs it, paying for a second piece of infrastructure (its own availability story, its own operational surface) to solve a scaling problem they don't yet have.

## Standard practice

- Never let a claim block a competing worker — `FOR UPDATE SKIP LOCKED`, not plain `FOR UPDATE`, for any table multiple workers poll concurrently.
- A lease always needs a fence. Match completion/failure writes on the exact claim identity (here, `locked_by` *and* `locked_at`), never on job id and worker id alone — see the core concepts above for why the realistic collision is the same worker id at two different epochs, not two different worker ids.
- Every test in `test/queue.test.js` marked as carrying a lesson was verified by deliberately mutating the implementation and confirming the test failed for real, not just inspected for plausibility — see the red commit's body for each mutation and its real failure output.
- Never compute a retry or lease deadline on the app process's clock and then compare it against the database's clock in a later query — see the millisecond-truncation note above for the real bug this caused during development.
- Always jitter a backoff, and prefer full jitter over equal jitter — the two are not equally good, per the simulations below. Full jitter versus decorrelated jitter is a closer call; either is defensible.
- Dead-letter anything that exceeds a retry budget, and make sure the dead-letter path is queryable and retryable by an operator (`GET /api/jobs?status=dead`, `POST /api/jobs/:id/retry`) — a dead job nobody can see or retry is just a silent failure with extra steps.
- Release, don't abandon: a graceful shutdown that still has work in flight past its deadline must actively release those leases, not just stop the process and let the reaper eventually notice.

## What this toy skips

- **No priority aging.** A job enqueued at low priority during a sustained flood of higher-priority work can wait indefinitely — nothing here promotes a job's priority the longer it waits, which a production scheduler (or a proper weighted-fair-queueing implementation) typically does.
- **No per-kind concurrency limits**, only per-account. A single expensive job `kind` can still monopolize every worker slot if enough of them are enqueued at once; a real system usually caps concurrency per kind as well as per tenant.
- **The fairness cap only prevents starvation within a single claim batch and against already-`running` jobs** — it does not track a moving window of recent throughput per account, so it can't detect or throttle an account that claims-and-completes jobs unusually fast across many consecutive small batches.
- **The per-account cap is advisory, not a hard invariant, under real concurrent claiming.** `running_counts` reads a snapshot of already-committed `running` rows at the start of the statement; it cannot see another claim that is concurrently in flight in a different, not-yet-committed transaction. Two workers claiming at the same instant can each compute the same "N currently running for this account" count and each admit candidates against it, so the account's true concurrent running count can briefly exceed `perAccountLimit` by a small margin. The cap bounds sustained starvation; it is not a strict ceiling enforced against every possible interleaving.
- **No visibility/metrics endpoint for queue depth or lag**, the two numbers the README of any alerting system built on top of this queue would need most (see `docs/plan.md`'s dropped alerting task) — an operator has to query `/api/jobs` and reason about it manually.
- **A single hardcoded `leaseMs` for every job kind.** A real system usually lets a slow job kind declare its own expected lease rather than forcing every kind through one global default.
- **No idempotency key beyond the handler's own discipline.** `send_message`'s idempotency comes entirely from `messagesRepo.beginSending`'s status guard; a handler that forgets to claim before it sends has no queue-level safety net forcing it to be replay-safe.

## In the real world (AWS / GCP)

How this exact design evolves once you stop running one Postgres and one Node process:

- **The lease is SQS's visibility timeout, almost verbatim.** On AWS the whole claim/lease/reaper/heartbeat block collapses into **SQS**: `ReceiveMessage` is `claimJobs`, the visibility timeout is `lease_expires_at`, `ChangeMessageVisibility` is the heartbeat, `maxReceiveCount` + a redrive policy is `max_attempts` + the dead-letter status, and the DLQ console redrive is `POST /api/jobs/:id/retry`. What you lose against this toy: no `ORDER BY priority`, no per-account fairness (SQS is FIFO-per-message-group or nothing), and no SQL query over queue state — "show me every dead job with its last error" becomes a separate table you maintain yourself.
- **On GCP the same role is Cloud Tasks or Pub/Sub.** **Cloud Tasks** when you want this app's shape (a task targets an HTTP endpoint, has a schedule time = `run_at`, per-queue rate and concurrency caps ≈ a crude fairness control, automatic retry with configurable backoff = `backoffMs`); **Pub/Sub** when consumers pull a stream — its ack deadline is the lease (`modifyAckDeadline` = heartbeat), and a dead-letter topic after N delivery attempts is the `dead` status.
- **Workers stop being a `setInterval`.** On AWS the poll loop disappears into a **Lambda event source mapping** on the queue (concurrency limit ≈ `concurrency`), or stays a long-polling loop in an ECS/Fargate service when jobs outlive Lambda's 15-minute cap. On GCP: Pub/Sub push into **Cloud Run** (Cloud Run's max-instances is your concurrency cap), or a pull loop in a Cloud Run worker pool / GKE deployment.
- **What survives the migration untouched: idempotent handlers.** Both SQS and Pub/Sub are at-least-once, exactly like this queue — the `beginSending` status-claim discipline is the part you keep no matter which broker you buy. FIFO SQS and Pub/Sub's exactly-once-delivery mode narrow the duplicate window; neither removes the need for a receiver-side guard once a side effect leaves the broker's transaction.
- **When to keep Postgres anyway.** The core concepts above already say it: teams reach for SQS/Pub/Sub long before volume demands it. A Postgres queue keeps jobs and business data in one transactional boundary — the enqueue in `POST /api/messages` is atomic with the message row, which no external broker can offer without reintroducing the outbox pattern in front of itself. The honest production trigger to move: claim contention you can measure, or needing the broker's fan-out/ordering features, not fashion.

## Try it

Requires `jobs` migrated (`npm run migrate`) and a fake upstream to receive deliveries — a bare `node:http` server that just logs what it gets:

```js
import http from 'node:http'
http.createServer((req, res) => {
  let body = ''
  req.on('data', (chunk) => { body += chunk })
  req.on('end', () => { console.log('received', body); res.writeHead(200); res.end() })
}).listen(4900, '127.0.0.1', () => console.log('fake upstream on 4900'))
```

```bash
node fake-upstream.js &
npm run seed
npm run dev
curl -s http://localhost:5004/api/jobs
```

Within a couple of `WORKER_POLL_MS` ticks (default 500ms), the seeded `send_message` jobs move from `ready` to `done` and the fake upstream's log shows both deliveries; the seeded `always_fails` job (an intentionally unregistered `kind`) exhausts its two attempts and lands `dead` with `last_error: "no handler registered for kind \"always_fails\""`. Retry it directly:

```bash
curl -s -X POST http://localhost:5004/api/jobs/<id>/retry
```

## Further reading

- [PostgreSQL documentation — `SELECT` (the locking clause)](https://www.postgresql.org/docs/current/sql-select.html) — the exact line this claim's non-blocking behaviour rests on: "skipping locked rows provides an inconsistent view of the data... but can be used to avoid lock contention with multiple consumers accessing a queue-like table."
- [Amazon SQS — Visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html) — the lease this queue's `lease_expires_at` is modeled on, in the system that made the pattern standard: default 30 seconds, extendable with a heartbeat-style call, and explicit that at-least-once still applies even with it.
- [Amazon SQS — Using dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html) — `maxReceiveCount` as the direct analogue of this queue's `max_attempts`, and the same operator workflow this queue's dead-letter endpoints support: examine what landed there, diagnose why, and redrive it.
- [Martin Kleppmann — How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html) — the fencing-token argument this queue's `locked_at` equality check implements: a lease alone cannot tell a dead holder from a merely slow one, and a monotonically increasing token checked at write time is what closes that gap.
- [AWS Architecture Blog — Exponential Backoff and Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) — the simulated results this queue's `backoffMs` formula (`random() * min(cap, base * 2 ** attempts)`) is drawn from: full jitter clearly beats equal jitter, but the comparison against decorrelated jitter is described as "less clear."

Elsewhere in this repo: [`sql-ledger/src/outbox/README.md`](../../../sql-ledger/src/outbox/README.md) for the pattern this queue is deliberately not — a claim that only ever reads — and the same `SKIP LOCKED` non-blocking argument made from the outbox's side; [`mern-shop/server/src/idempotency/README.md`](../../../mern-shop/server/src/idempotency/README.md) for the same lease-without-a-fence failure mode (two owners, one document, a silently corrupted store) worked through in full on a different schema; [`mern-tickets/server/src/circuitBreaker/README.md`](../../../mern-tickets/server/src/circuitBreaker/README.md) for why retries interact badly with a circuit breaker sitting in front of the same dependency this queue's handlers call out to.
