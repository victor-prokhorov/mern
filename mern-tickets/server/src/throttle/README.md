# Throttling

## What this is

A token bucket per user per action, persisted in MongoDB, that limits how fast one caller can create tickets or post comments while still allowing short bursts. It answers "how fast is this one actor allowed to go," not "how much total load can the service take."

## How it works here

`consume(userId, action, now)` (`src/throttle/tokenBucket.js:29`) loads (or creates) a bucket document keyed by `${userId}:${action}` (e.g. `64f.../ticket:create`), computes how many tokens the elapsed time since `updatedAt` would refill via `computeRefill` (`src/throttle/tokenBucket.js:9`), and — if at least one token is available — writes back `tokens: refilled - 1` and bumps `updatedAt` to `now`. `computeRefill` is a pure function: `min(burst, tokens + elapsedMinutes * refillPerMinute)`, capped at the bucket's burst size so idle time cannot accumulate an unbounded credit.

The write in `consume` is a compare-and-swap: `buckets.updateIfUnchanged` (`src/repositories/tokenBuckets.js:11`) matches on `_id`, `updatedAt`, and `tokens` together as they were just read, so if a concurrent request already modified the same bucket, the update matches nothing, returns `null`, and `consume` retries the whole read-compute-write cycle (`src/throttle/tokenBucket.js:32-43`) from the fresh state — this is what "atomic" means here: no two concurrent requests can both believe they spent the same token. `now` is captured once, as a default argument, and reused across all ten attempts, so a retry re-reads the bucket but does not re-read the clock; the refill a losing request sees is the refill it would have seen on its first try. Under heavy enough contention for the same bucket, that retry loop can still run out of attempts; when it does, `consume` reports `{ allowed: false, tokens: 0, retryAfter: 1 }` rather than throwing, so a caller who loses every race still gets a normal 429 with a short `Retry-After` instead of a 500 — contention is treated as "try again in a second," not a server error.

`throttle(userId, action)` (`src/throttle/tokenBucket.js:47`) is the enforcement wrapper services call: it consumes a token and, if none were available, throws `TooManyRequestsError('too many requests', retryAfter)`. The error middleware (`src/middleware/error.js`) turns that into a 429 with a `Retry-After` header set to `retryAfter` seconds — computed by `retryAfterSeconds` (`src/throttle/tokenBucket.js:14`) as the time until the deficit between the current (fractional) token count and 1 whole token would be refilled at this bucket's rate, rounded up so the client is never told to retry too early.

`RATES` (`src/throttle/tokenBucket.js:4`) configures two buckets: ticket creation (burst 5, refill 1/minute) and comment creation (burst 20, refill 5/minute). `create` and `addComment` (`src/services/tickets.js:39`, `src/services/tickets.js:116`) each call `throttle` before doing anything else expensive, so a caller who is over their limit is rejected as cheaply as possible. Note the exact ordering in `create`: `authorize` (`:36`), input validation (`:37-38`), `throttle` (`:39`), then the hook pipeline (`:40`). A submission that the moderation hooks are about to reject has therefore already spent a token. That is deliberate — you do not want to pay for a database round trip and a keyword scan before deciding whether the caller is allowed to be asking at all — but it means the throttle counts attempts, not accepted work, and a client stuck in a rejection loop burns its budget on rejected requests.

## The core concepts

- **The words are not standardized, and you should say which ones you mean.** "Rate limiting," "throttling" and "quota" are used interchangeably across vendors, so treat the following as this document's usage rather than as an industry definition. The distinction that *is* well drawn in practice is Stripe's, between a limiter and a shedder: a limiter decides from the *requesting user's own recent history*, while "a load shedder makes its decisions based on the whole state of the system rather than the user who is making the request." That line is worth keeping even when the labels around it move.
- **Rate limiting**, as used here, protects the service as a whole from aggregate load — typically enforced per IP address at a reverse proxy or gateway, in front of authentication, because its job is to stop the service falling over before it even knows who is asking.
- **Throttling** (what this module does) shapes one authenticated actor's sustained rate over time while still allowing a burst — the actor is known, the limit is per-identity, and a short spike is expected and tolerated. In Stripe's taxonomy this is a request rate limiter, and they run it alongside a concurrent-requests limiter for the endpoints where the expensive thing is not the request count but how many are in flight at once.
- **Quotas** are a billing/entitlement concept over a long period (1,000 tickets per month), not a request-rate concept — a quota can be exhausted and still leave a caller able to make requests slowly; a throttle limits speed, not total count over unbounded time.
- **Backpressure** is what a queue or worker pool does when it cannot keep up with accepted work — signaling "slow down" or shedding load internally, downstream of acceptance, rather than rejecting a request before accepting it at all. Do not conflate it with load shedding: backpressure propagates a slow-down signal upstream so producers stop producing, whereas shedding drops work outright. The argument for shedding is about goodput rather than throughput — as the Amazon Builders' Library puts it, a server that keeps accepting work while overloaded spends its time context switching and becomes too slow to be useful, so refusing excess work *cheaply* is what keeps the accepted work fast.
- **Token bucket** vs. **leaky bucket**: a token bucket accumulates capacity while idle (up to `burst`) and spends it in a burst, which matches "let someone catch up after being quiet, but not sustain it forever." A leaky bucket instead smooths output to a constant rate regardless of arrival pattern, which suits shaping outbound traffic rather than describing what an actor is allowed to do.
- **GCRA (generic cell rate algorithm)**: the same burst-plus-sustained-rate shape as a token bucket, expressed with one stored value instead of two. Rather than a token count and a timestamp, it stores a single *theoretical arrival time* (TAT): a request is allowed if the current time is at or after `TAT - (τ + T)`, where `T` is the emission interval (the reciprocal of the sustained rate) and `τ` is the burst tolerance; on acceptance the TAT advances by `T`. It comes from ATM traffic policing, and the practical reason to reach for it is that it is exactly one comparison and one write against one field, which is easier to make atomic in a datastore than this module's read-compute-compare-and-swap loop.
- **Not every request costs the same.** One token per request is the simplest possible cost model and it is wrong the moment endpoints differ in expense. Shopify's GraphQL Admin API is the clean production counterexample: on the standard tier the bucket holds 2,000 points and restores 100 points per second (both doubled from 1,000/50 in early 2024, and higher plans get more), a query's cost is computed from its shape before it runs (a mutation costs 10, a connection costs 2 plus the objects returned), and the client is refunded the difference between the estimated and actual cost. Same algorithm, cost-weighted consumption.
- **Lazy refill**: tokens are computed on demand from elapsed wall-clock time at the moment of an actual request, not incremented by a periodic job. There is nothing to schedule, nothing idle actors cost the system, and the same formula is correct whether the last request was one second or one week ago.
- **429 and `Retry-After` are two different specifications.** The status code is RFC 6585 §4 — "the user has sent too many requests in a given amount of time" — and its guidance is that the response *should* explain the condition and *may* include `Retry-After`; it is not mandatory. The header itself is RFC 9110 §10.2.3, which allows either a delay in seconds or an HTTP-date, and lists 429 among the responses it may accompany. This module always sends the delay-seconds form. There is deliberately no *standard* way to tell a client how much budget it has left before it is rejected: the `RateLimit` and `RateLimit-Policy` header fields have been an IETF draft for years (`draft-ietf-httpapi-ratelimit-headers`, revision 11) and are still not an RFC, so anything you emit today is a convention, not a standard.

## Standard practice

- Compute refill from elapsed time on read, not a cron tick — a cron-based refiller has to run for every bucket whether or not anyone is asking, and its granularity becomes the limit's real precision.
- Cap refilled tokens at `burst` — otherwise a caller idle for a long time accumulates an unbounded credit and can burst far harder than the limit intends.
- Make the consume-and-decrement step atomic against concurrent requests for the same key — a naive read-then-write from application code is a race that lets two simultaneous requests both spend the last token. Compare-and-swap with a bounded retry, as here, is the portable version; a single-round-trip conditional update (Redis script, GCRA against one field) is the version you want under real contention.
- Key the bucket by both actor and action — a single global bucket per user would let heavy comment traffic starve that same user's ability to create a ticket, which is not what either limit is meant to express.
- Return `Retry-After` computed from the actual deficit, not a fixed constant — a fixed value is either too conservative (wasted client wait) or wrong (client retries too early and gets rejected again).
- Reject as early and as cheaply as the correctness of the check allows — the whole value of a limiter disappears if establishing that someone is over their limit costs as much as serving them.
- Decide, and document, whether the limiter counts attempts or accepted work. This one counts attempts (see the ordering note above); both are defensible, but a client that cannot tell which will retry wrongly.
- Have the client back off with capped exponential backoff and jitter rather than retrying on a fixed schedule — synchronized retries from many clients are how a limiter's 429s turn into a second outage.

## What this toy skips

- Per-IP rate limiting at the edge — this module only throttles authenticated actors; an unauthenticated flood of requests before `identify` runs is not addressed here at all. The layer this app is missing is exactly the one [`../../../../mern-shop/server/src/rateLimit/README.md`](../../../../mern-shop/server/src/rateLimit/README.md) implements: a fixed-window counter keyed by IP or by credential, applied in front of authentication, on a different mechanism (fixed window plus a TTL index) than the token bucket here.
- A sliding-window or leaky-bucket alternative — token bucket was chosen because "allow a burst, then settle to a sustained rate" is the desired shape for both tickets and comments. The production alternative worth knowing is Cloudflare's sliding-window approximation, which stores two counters per key and weights the previous window by its overlap with the floating one; measured against 400 million requests it wrongly allowed or limited 0.003% of them, with a 6% average difference between the approximate and real rate and no false positives.
- Cost-weighted consumption — every request costs exactly one token regardless of what it asks for.
- Load shedding — there is no notion of system-wide state here at all. A throttle that is per-user cannot protect the service from many users at once, which is the gap a shedder fills.
- Advertising remaining budget before rejection — no `RateLimit` headers, standardized or otherwise; a client learns its limit only by hitting it.
- Backoff coordination between client and server beyond a single `Retry-After` value — there is no exponential backoff policy communicated, just the time until the next token.
- Bucket cleanup. **This app now reaps them.** `src/models/tokenBucket.js` declares a TTL index on `updatedAt` with `expireAfterSeconds: IDLE_BUCKET_TTL_SECONDS` (one day), so a bucket belonging to a user who stopped being active — or who no longer exists — is deleted a day after its last touch instead of living forever. The relative form is the right one here: expiry is measured from `updatedAt`, unlike the companion fixed-window limiter in `mern-shop`, which stores an absolute `expiresAt` and uses `expires: 0`. Dropping an idle bucket is safe rather than merely tidy, because a bucket untouched for a day would have refilled to `burst` anyway (five minutes at `ticket:create`'s rate) — the row that gets deleted and the row that gets recreated on the next request hold the same answer. `deleteAll` still exists in the repository with nothing calling it, so re-seeding leaves the previous generation of buckets behind until the TTL sweep catches them.
- Anything distributed — one MongoDB collection is the single source of truth, which is fine at one process and becomes a hot-key contention problem, not a correctness problem, at scale. The retry loop's ten attempts is the only backstop, and it degrades to a spurious 429 rather than to a wrong answer.

## Try it

```
for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:5001/api/tickets \
    -H 'Content-Type: application/json' -H 'x-user-id: <rae id>' \
    -d "{\"title\":\"t\",\"body\":\"body $i\",\"priority\":\"normal\"}"
done
```

The first five print `201`; the sixth prints `429`. This assumes a fresh bucket, so run it as the first thing that user does: nothing resets `TokenBucket` documents on demand (`deleteAll` in `src/repositories/tokenBuckets.js` is exported and never called, and the only cleanup is the one-day TTL sweep on `updatedAt` described under "Bucket cleanup" above — far too slow to matter within a demo), so if this user has created a ticket in the last few minutes you will see fewer than five successes before the 429. Re-running `npm run seed` does give you a clean bucket, but only incidentally — it deletes and recreates the users, so their new `_id`s produce new bucket keys and the old documents are orphaned rather than reset. Run `curl -i` on that sixth request to see the header:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 60
...
{"error":"too many requests"}
```

`Retry-After: 60` because ticket creation refills one token per minute, and the bucket is a whole token short.

## Further reading

Specifications first, then people describing what they actually run.

- [RFC 6585 §4, Additional HTTP Status Codes: 429 Too Many Requests](https://www.rfc-editor.org/rfc/rfc6585.html) — the defining text for the status code, still current and not folded into the newer HTTP core RFCs. Short enough to read in full, and it settles that `Retry-After` on a 429 is optional.
- [RFC 9110 §10.2.3, HTTP Semantics: Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#field.retry-after) — the header's actual definition, including the HTTP-date form most implementations forget exists.
- [draft-ietf-httpapi-ratelimit-headers, RateLimit header fields for HTTP](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/) — the proposed standard way to advertise quota and remaining budget. Worth tracking, and worth checking its status before citing: it is an Internet-Draft, not an RFC.
- [Stripe, Scaling your API with rate limiters](https://stripe.com/blog/rate-limiters) — four different limiters running in production, why each exists, and roughly how often each fires. The limiter-versus-shedder distinction in this README comes from here.
- [Cloudflare, How we built rate limiting capable of scaling to millions of domains](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/) — the sliding-window approximation with real accuracy measurements against 400M requests. The best short answer to "why not just store all the timestamps."
- [Shopify Engineering, Rate limiting GraphQL APIs by calculating query complexity](https://shopify.engineering/rate-limiting-graphql-apis-calculating-query-complexity) — cost-weighted consumption in production: static cost analysis before execution, refunds when the estimate was too high, and the numbers behind the point system.
- [Amazon Builders' Library, Using load shedding to avoid overload (David Yanacek)](https://d1.awsstatic.com/builderslibrary/pdfs/using-load-shedding-to-avoid-overload.pdf) — why an overloaded server gets slower rather than merely busier, and why the right response is to refuse work quickly. This is the argument for cheap early rejection, made properly.
- [Amazon Builders' Library, Timeouts, retries, and backoff with jitter (Marc Brooker)](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf) — the other half of a rate limit: what a well-behaved client does with the 429 you just sent it. Capped exponential backoff plus jitter, and why the jitter is not optional.
- [Brandur Leach, Rate limiting, cells, and GCRA](https://brandur.org/rate-limiting) — the clearest write-up of GCRA in application terms: theoretical arrival time, emission interval, burst tolerance, and why removing the background drip makes the algorithm easier to implement correctly.
