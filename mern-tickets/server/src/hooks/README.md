# Hook registry

## What this is

A minimal synchronous pipeline: `register(event, handler)` attaches a function to a named event, `run(event, payload)` calls every handler registered for that event in order, letting each one continue, reject, or rewrite the payload for the next one. Ticket and comment creation run their payload through this pipeline before anything is persisted.

## How it works here

`register` (`src/hooks/registry.js:7`) appends a handler to an array keyed by event name in a module-level `Map` (`src/hooks/registry.js:3`) — registration order is preserved because it is just array push order. `run` (`src/hooks/registry.js:35`) walks that array for the given event, threading a `current` payload through each handler: a handler's return value is inspected for its `action` field, and `continue` (or a thrown error) moves to the next handler with `current` unchanged; `reject` returns immediately from `run` with `{ action: 'reject', reason }`, so no handler after it ever runs; `transform` replaces `current` with `result.payload`, but only when `result.payload` is actually present — a `transform` result with no `payload` field is treated as a no-op rather than wiping the pipeline's payload to `undefined` (`src/hooks/registry.js:46-48`). If every handler continues, `run` returns `{ action: 'continue', payload: current }` with whatever the last transform left behind.

Each handler call is wrapped in `withTimeout` (`src/hooks/registry.js:18`), which races the handler against a fixed budget — `HANDLER_TIMEOUT_MS` is 50 ms (`src/hooks/registry.js:5`) — clearing the timer as soon as the handler settles either way and `unref`-ing it so a pending one never blocks process exit. This is a race, not a cancellation: JavaScript has no way to abort an in-flight promise, so a handler that overruns its budget keeps running to completion in the background with its result discarded. If that handler had side effects, they still happen, just unobserved. A timeout is treated as a thrown error. Both a genuine throw and a timeout are caught in the same place (`src/hooks/registry.js:40-45`): the error is logged and the loop moves on to the next handler as if this one had returned `continue`.

This is fail-open by construction, and it is worth being blunt about the consequence rather than describing it as "degraded moderation": a `reject` that would have fired is downgraded to a `continue`. If `keywordBlockerHandler`'s database query for `BlockedTerm` rows takes longer than 50 ms, content that contains a `block`-severity term is saved. Two of the three handlers here do a database round trip inside that 50 ms budget, so this is not a hypothetical failure mode, it is what a slow Mongo produces.

`src/hooks/bootstrap.js` registers three handlers on both `ticket:before-create` and `comment:before-create`, in this order: `keywordBlockerHandler` (the keyword blocker — scans the payload text, returns `reject` for a `block`-severity match or `transform`s in `moderation: { flagged: true, terms: [...] }` for a `flag`-severity match), `linkLimitHandler` (counts URLs in the body; more than three `transform`s in the same `moderation.flagged` shape, appending `'link-limit-exceeded'`), and `duplicateContentHandler` (rejects if the same author submitted the identical body within the last 60 seconds). `registerModerationHooks` (`src/hooks/bootstrap.js:42`) is called once, at module load, from `src/app.js`.

That order is load-bearing, not cosmetic. `linkLimitHandler` reads `payload.moderation.terms` (`src/hooks/bootstrap.js:25`) and appends to it, so it depends on `keywordBlockerHandler` having already run and written that field; registered the other way round, the keyword blocker's `transform` would build a fresh `moderation` object and discard `'link-limit-exceeded'`. The registry cannot express or check that dependency — see "The core concepts."

`create` and `addComment` (`src/services/tickets.js:40`, `src/services/tickets.js:117`) call `runHooks(event, payload)` after the throttle check and before touching the database, and inspect the outcome: `reject` becomes a 400 with `outcome.reason` as the message (`src/services/tickets.js:41`, `src/services/tickets.js:118`); otherwise the (possibly transformed) `outcome.payload` — including any `moderation` field a handler attached — is what gets persisted.

## The core concepts

- **Hooks vs. middleware vs. events vs. webhooks**: middleware (Express's) is tied to the HTTP request/response cycle and runs in route order; an event emitter (Node's `EventEmitter`) is fire-and-forget with no way for a listener to reject or rewrite what triggered it, and its `emit` is synchronous but returns only whether anyone was listening; a webhook is an HTTP callback to a different process, with all the latency and failure modes that implies. This registry is closest to a synchronous, in-process event system where listeners can veto or edit the thing that is happening — closer to a "before save" hook in an ORM than to any of the above.
- **Sync vs. async moderation, and the latency/consistency tradeoff**: running every handler inline, in the request, means the caller's response already reflects the final decision (rejected, flagged, or clean) — simple to reason about, but the request is only as fast as the slowest handler, and a slow external classifier would make every ticket creation slow. An async design decouples latency from moderation cost, at the price of a window where content exists before its moderation decision is final, and the API surface has to expose that (a `pending` status, a webhook, a poll). This app chooses sync because a teaching example should let you see the whole decision in one response.
- **The async version has a name, and the naive form of it is broken.** "Publish the payload and moderate in a worker" is two writes — save the record, then publish the message — with no atomicity between them, so a crash in the middle either loses the moderation job or moderates something that was never saved. The pattern that fixes it is the *transactional outbox*: write the message into an outbox table in the same database transaction that writes the entity, and let a separate relay process read the outbox and publish. Chris Richardson's canonical statement of it is that this avoids two-phase commit and makes messages "guaranteed to be sent if and only if the database transaction commits" — and its stated drawback is that the relay can publish duplicates, so consumers must be idempotent. That drawback is the entire reason the next bullet exists. This repo has a working outbox to read against the description: [`../../../../sql-ledger/src/outbox/README.md`](../../../../sql-ledger/src/outbox/README.md), including the at-least-once delivery the drawback describes and the `FOR UPDATE SKIP LOCKED` claim loop that makes the relay safe to run more than once.
- **Idempotency, and what this pipeline does not have**: idempotency in the HTTP sense is a *client-supplied key* and a server-side record of the first result. Stripe's implementation is the reference: the client generates the key, the server saves the resulting status code and body of the first request under it — success or failure alike — and replays that same stored result for any retry, prunes keys after at least 24 hours, and errors if a key is reused with different parameters. `duplicateContentHandler` is not that. It dedupes on the *content* of the body within a 60-second window, has no key, stores no prior result, and answers a retry with a fresh 400 `duplicate submission` rather than the original 201 and the original ticket. That difference matters to a client: a genuine idempotent retry is supposed to be indistinguishable from the original call, whereas here a client that retries a request whose response it never saw gets an error and no way to find out whether the first attempt landed. Content dedup is a spam control that happens to catch some retries; it is not an idempotency mechanism. The real thing is implemented in this repo, one app over: [`../../../../mern-shop/server/src/idempotency/README.md`](../../../../mern-shop/server/src/idempotency/README.md) takes a client-supplied key, claims it against a unique index, stores the first response and replays it verbatim — read it beside this bullet to see exactly which pieces `duplicateContentHandler` does not have.
- **Ordering and priority**: handlers run in registration order with no separate priority field and no declared dependencies. That is a real limitation, and this pipeline is already relying on it — `linkLimitHandler` reads a field `keywordBlockerHandler` writes, so correct output depends on a registration order that nothing enforces or documents outside `bootstrap.js`. A registry with priorities, or with declared reads/writes, would turn that from a convention into a check.
- **Failure modes and fail-open vs. fail-closed by domain**: this registry is fail-open — a throwing or timing-out handler is skipped and the request proceeds as if that handler said `continue` (`src/hooks/registry.js:40-45`). That is the right default for moderation: if the keyword blocker's database call fails, a support ticket still needs to get filed and reach a human, and a missed flag is far cheaper than blocking every ticket in an outage. A payments hook (fraud check before charging a card) should typically fail closed instead — if the fraud check cannot run, do not charge the card — because there the cost of a false negative (an uncaught bad transaction) is higher than the cost of blocking a good one. The right default is a property of what the hook protects, not a property of "hooks" in general. The choice is only defensible if the skip is *visible*: fail-open plus a silent skip is indistinguishable from a handler that decided everything was fine.
- **Timeouts and circuit breakers**: each handler gets a fixed 50 ms budget so one slow handler cannot stall the whole pipeline indefinitely. There is no circuit breaker here — a handler that times out on every single request still gets tried, and still costs the full 50 ms, on every single request. A circuit breaker is the standard fix, and it has a precise shape: Michael Nygard's pattern, as Fowler describes it, wraps the call in an object that counts failures and, once they pass a threshold, *trips* — moving from **closed** (calls pass through) to **open** (calls fail immediately without attempting the protected call), and after a timeout to **half-open**, where a trial call decides whether to close again or re-open. The point is not just to fail faster; it is to stop hammering a dependency that is already struggling. This app has one, just not here: [`../circuitBreaker/README.md`](../circuitBreaker/README.md) wraps the outbound webhook with exactly that three-state machine. The reason it protects the webhook and not the hook pipeline is worth stating, because it is the criterion for where a breaker belongs: the webhook is a call to a *remote* dependency that can be down independently of this process, so failing fast genuinely saves a timeout and genuinely relieves the dependency. A hook handler is in-process, and its slowest case (a Mongo query) is a dependency the rest of the request needs anyway — tripping a breaker there would not stop the load, it would just skip moderation more aggressively than the timeout already does.
- **Observability of a pipeline that silently mutates content**: a `transform` can change what gets saved without the caller ever being told which handler did it or why (this is deliberate for moderation — see [`../moderation/README.md`](../moderation/README.md) on not naming the matched term). A skipped handler now logs through the structured logger (`logger.error('hook handler failed', { event, error })`, `src/hooks/registry.js:43`) rather than a bare `console.error`, so the line is a JSON object with `requestId`/`userId`/`route` attached by [`../observability/README.md`](../observability/README.md) rather than free text — but it is still only a log line: which handler *transformed* a given field, and why, is still not recorded anywhere, and there is still no counter an operator can alert on.

## Standard practice

- Keep the contract to exactly three actions (`continue`, `reject`, `transform`) — a handler that can return anything else makes every call site guess at what happened.
- A `reject` always short-circuits, unconditionally — a moderation handler that runs after a rejection could act on content that is never actually going to be saved.
- Catch both thrown errors and timeouts in the same place, and treat them the same way — a handler that hangs and a handler that throws are the same failure from the pipeline's point of view (it didn't get an answer in time), so they should have the same fallback behavior.
- Decide fail-open vs. fail-closed per domain, explicitly, and write down why — "moderation fails open, payments fail closed" is not a rule that generalizes; it has to be re-derived for whatever the next hook protects.
- Make the fail-open path loud. A skipped handler should raise a counter an operator alerts on, not only a log line, because the failure is invisible in the response by design.
- Set the timeout budget from what the handler actually does. 50 ms is generous for a pure function and tight for a database round trip; a single global constant guarantees one of the two is wrong.
- Register handlers in one place, at startup (`registerModerationHooks`) — scattering `register` calls across the codebase makes "what runs on this event, in what order" impossible to answer by reading one file.
- Do not call a content-dedup check an idempotency mechanism, in code or in an API contract. If clients need safe retries, take a client-supplied key and replay the stored response.

## What this toy skips

- Priority or dependency ordering between handlers — only registration order, which the current handler set already depends on.
- Circuit breaking for a chronically failing or slow handler — it is retried (and timed out) on every request regardless of recent history. [`../circuitBreaker/README.md`](../circuitBreaker/README.md) is the same app's breaker, applied to the outbound webhook instead; the concept bullet above says why it is there and not here.
- Cancellation. `withTimeout` abandons the result but cannot stop the work; an `AbortController` passed into the handler is the shape a real version would take.
- Per-handler observability — a failure now carries request correlation (see [`../observability/README.md`](../observability/README.md)), but there is still no per-handler counter and nothing to alert on.
- An async/queue execution mode, and therefore the outbox that a correct one would need — the pipeline is synchronous only; see "Sync vs. async moderation" above for what that costs and what it buys.
- Idempotency keys and stored responses — see the concept above for why `duplicateContentHandler` is not a substitute.
- Handler-level configuration (e.g., a different timeout budget per handler) — `HANDLER_TIMEOUT_MS` is one global constant shared by a pure function and two database queries.
- Persisting the fact that a handler was skipped due to a timeout/throw anywhere a human could later audit — it is a log line, not a record.

## Try it

```
curl -s -X POST http://localhost:5001/api/tickets \
  -H 'Content-Type: application/json' -H 'x-user-id: <rae id>' \
  -d '{"title":"t","body":"same body twice","priority":"normal"}'

curl -s -X POST http://localhost:5001/api/tickets \
  -H 'Content-Type: application/json' -H 'x-user-id: <rae id>' \
  -d '{"title":"t2","body":"same body twice","priority":"normal"}'
```

The second call returns 400 `{"error":"duplicate submission"}` — the `duplicateContentHandler` rejected it because the same reporter submitted the identical body less than 60 seconds earlier. Three things have to hold for this to work, and each is a property of the pipeline worth noticing: both calls must be by the *same* user (the handler queries by author), within 60 seconds (`DUPLICATE_WINDOW_MS`), and by a user the policy engine lets create tickets at all — an `agent` gets 403 here rather than 400, because no rule permits `ticket:create` for that role and `authorize` runs before the pipeline does. Note also that the differing `title` makes no difference: only `body` is compared.

## Further reading

Each of these is the canonical statement of a pattern this README names, so that "we do X" can be checked against what X actually is.

- [Chris Richardson, Transactional outbox pattern](https://microservices.io/patterns/data/transactional-outbox.html) — the async alternative to this pipeline, stated with its problem, solution and drawbacks in about a page. The drawback line ("the message relay might publish a message more than once") is the one that leads directly to idempotent consumers.
- [Martin Fowler, CircuitBreaker](https://martinfowler.com/bliki/CircuitBreaker.html) — closed, open and half-open, with the failure threshold and reset timeout spelled out, and the attribution to Michael Nygard's *Release It!* where the pattern was popularized. Short, with worked code.
- [Stripe API reference, Idempotent requests](https://docs.stripe.com/api/idempotent_requests) — the reference implementation of an idempotency key: client-generated, first result stored and replayed, keys pruned after 24 hours, parameter mismatch is an error. Read this before calling anything in your own system idempotent.
- [draft-ietf-httpapi-idempotency-key-header, The Idempotency-Key HTTP Header Field](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) — the attempt to standardize the above. Cited with a caveat you should check for yourself before relying on it: the draft has expired without becoming an RFC, so today this is a widely copied vendor convention, not a standard.
- [Amazon Builders' Library, Timeouts, retries, and backoff with jitter (Marc Brooker)](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf) — how to pick a timeout that is neither cargo-culted nor arbitrary, and why retrying without jitter turns a blip into an outage. Directly relevant to the single global 50 ms constant here.
- [Amazon Builders' Library, Using load shedding to avoid overload (David Yanacek)](https://d1.awsstatic.com/builderslibrary/pdfs/using-load-shedding-to-avoid-overload.pdf) — the case that a system under load gets slower rather than merely busier, which is the mechanism by which a 50 ms handler budget starts being exceeded in production long before anything looks broken.
- [Node.js documentation, Events](https://nodejs.org/api/events.html) — worth reading precisely because this registry is *not* an `EventEmitter`: listeners cannot veto, `emit` returns a boolean rather than a decision, and error handling is a special-cased `'error'` event. The contrast is the clearest way to see what this module adds.
- [Express, Using middleware](https://expressjs.com/en/guide/using-middleware.html) — the other thing this is often confused with. Middleware is ordered by mounting and scoped to the request/response cycle; hooks here are ordered by registration and scoped to a domain event that may have no request behind it.
- [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) — for the fail-open visibility problem: what a security-relevant event log should contain, and why "we logged it to stderr" is not an answer.

Elsewhere in this repo: [`../moderation/README.md`](../moderation/README.md) for the first and most consequential handler in the pipeline; [`../throttle/README.md`](../throttle/README.md) for the check that runs immediately before it and has already spent a token by the time a handler rejects; [`../policy/README.md`](../policy/README.md) for the check that runs before both; [`../tickets/README.md`](../tickets/README.md) for what happens to `outcome.payload` once the pipeline is done with it.
