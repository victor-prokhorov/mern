# Authorization policy engine

## What this is

A small policy decision point: given who is asking, what they want to do, and to what, it returns a decision with a reason, and every ticket service function calls it before doing anything. This is authorization (what you're allowed to do), not authentication (who you are) — see [`../tickets/README.md`](../tickets/README.md) for how identity is established here.

## How it works here

`decide(ruleSet, request)` (`src/policy/engine.js:11`) is the pure decision function: it filters `ruleSet` down to the rules that match the request (`ruleMatches`, `src/policy/engine.js:4`), then applies **deny-overrides** — if any matching rule denies, the result is deny regardless of any matching permit (`src/policy/engine.js:13-14`) — and falls through to **default deny** if nothing matched at all (`src/policy/engine.js:17`).

`authorize(request)` (`src/policy/engine.js:20`) is the enforcement wrapper: it calls `decide` against the real policy set in `policies.js`, logs the ruleId and reason to the server console on a deny, and throws `ForbiddenError('forbidden')` — a generic message, because the caller does not get to learn which rule stopped them or why (`src/policy/engine.js:22-24`).

Every mutating and reading ticket service function calls `authorize` before touching data: `create` (`src/services/tickets.js:34`), `get` (`src/services/tickets.js:68`), `transitionStatus` (`src/services/tickets.js:78`), `assign` (`src/services/tickets.js:90`), `addComment` (`src/services/tickets.js:103`). Controllers never check a role themselves — they pass `req.subject` (set by `identify`, `src/middleware/identify.js`) straight through to the service, which builds the `{ subject, action, resource, context }` request and asks the engine. The `context` slot exists but is always `{}`: NIST's ABAC definition includes environment conditions (time of day, device posture, network location) as a first-class input, and this engine has the shape for them and uses none.

`policies.js` holds the rule set as one array, each rule `{ id, effect, actions, roles, reason, condition }`. The six rules: reporters may create tickets and may read/comment on tickets they reported (`ownsTicket`, `src/policy/policies.js:1-3`); agents may read, comment, transition and assign tickets in their own team (`sameTeam`, `src/policy/policies.js:5-7`); admins get a wildcard permit on every action; an explicit deny rule blocks even admins from `ticket:delete`, which only means something because deny-overrides beats the wildcard permit; and a deny rule blocks anyone but an admin from transitioning a ticket whose `resource.status` is `closed` (`ticketIsClosed`, `src/policy/policies.js:9-11`) — a condition on resource state, not on role alone. One consequence is easy to miss reading the rules quickly: no rule permits `ticket:create` for an `agent`, so agents cannot open tickets at all, only act on tickets already in their team.

`GET /api/tickets` (list) does not call `authorize` per row. Instead `list` (`src/services/tickets.js:56`) scopes the database query itself: reporters only ever see their own tickets, agents only their team's. This is a pragmatic stand-in for row-level authorization on a collection endpoint — see "What this toy skips" for the gap it leaves. `test/tickets.test.js`'s "list scoping" suite pins this down directly: it asserts a reporter or agent cannot see out-of-scope tickets even when every query filter matches, and was confirmed to fail if either scoping line in `list()` is removed.

## The core concepts

- **Authentication vs authorization**: authentication answers "who is this"; authorization answers "what can they do." This app's authentication is a placeholder (`x-user-id`); its authorization is real and independently testable.
- **RBAC (role-based access control)**: permissions attached to a role (`reporter`, `agent`, `admin`). The reference model here is the NIST/Ferraiolo-Kuhn model, standardized as ANSI INCITS 359-2004 and now maintained as INCITS 359-2012 (reaffirmed 2022); it defines core RBAC plus hierarchical roles and static/dynamic separation-of-duty constraints, none of which this engine has. Scales well until you need per-resource nuance.
- **ABAC (attribute-based access control)**: NIST SP 800-162 defines it as evaluating attributes of the subject, the object, the requested operation and, in some cases, environment conditions against policy. Here that means "is this my ticket," "is this ticket in my team," "is this ticket closed" — subject and object attributes only. RBAC alone cannot express "your own tickets"; ABAC conditions can. This engine is RBAC plus ABAC conditions, which is where most real systems land before reaching for a dedicated policy language.
- **ReBAC (relationship-based access control)**: permissions derived from a graph of relationships (Google Docs sharing, org charts). Google's Zanzibar is the reference design: it stores relation tuples of the form `object#relation@user`, where the user side may itself be a *userset* (another object's relation), and namespace configurations declare rewrite rules that derive relations from other relations, so "editors are also viewers" is a config line rather than duplicated tuples. The hard parts it solves are consistency (its "zookie" tokens let a client demand a snapshot no older than the ACL change it just made) and scale, not graph traversal as such. Not needed here because the relationships are shallow (owns / same-team), but it is the next step when "my team" becomes "my team, my manager's team, and anyone I shared this with."
- **PDP / PEP / PIP / PAP**: XACML's names for four separable roles. The Policy Decision Point is `decide` — the entity that evaluates policy and renders a decision. The Policy Enforcement Point is every service function calling `authorize` and letting it throw — the entity that makes the decision request and enforces the answer. The Policy Administration Point is `policies.js` — where a human edits the rules. The Policy Information Point is, in XACML's words, the entity that *acts as a source of attribute values*: this app has no such entity, because the only attributes any condition reads (`reporter`, `teamId`, `status`) are already on the resource the service loaded, so the attribute fetch and the decision happen in one function in one process. Naming these separately matters because in real systems they are often different processes or even different services, and a PIP that has to go and fetch an attribute is where latency and failure modes enter an authorization decision.
- **Default deny**: an empty or non-matching policy set produces deny, never permit. The alternative (default permit) means every unanticipated action is allowed, which is the wrong failure mode for access control. Note the small vocabulary difference from XACML: a XACML PDP returns one of Permit, Deny, NotApplicable or Indeterminate, and it is the PEP that is configured deny-biased so that NotApplicable and Indeterminate both become a refusal. `decide` collapses that inside the PDP by returning `deny` with `ruleId: null` when nothing matched, which is simpler and loses the ability to tell "no rule spoke" apart from "a rule said no" at the enforcement point — the `ruleId` is the only thing that distinguishes them, and only in the log.
- **Deny-overrides**: when rules conflict, deny wins. The alternative (permit-overrides) means one overly broad permit rule can silently punch a hole through every deny rule meant to constrain it — which is exactly what the `admin-no-delete` / `admin-wildcard` pair in this policy set is built to demonstrate. It is worth knowing that this is a choice, not a law, and that the major systems make it differently. XACML defines deny-overrides as one of a set of selectable rule- and policy-combining algorithms (permit-overrides, first-applicable, only-one-applicable, deny-unless-permit, permit-unless-deny, plus ordered variants), and you name the one you want per policy. AWS Cedar fixes the behaviour instead: an explicit `forbid` always overrides any `permit`, an empty policy set is an implicit deny, and neither is configurable. OPA/Rego supplies no combining algorithm at all — you write the conflict resolution yourself in Rego, and two complete rules that produce different values for the same document are an evaluation error rather than a conflict to be resolved. This engine hardcodes deny-overrides the way Cedar does.
- **Policies as data**: the rule set is an array of plain objects, not `if` statements scattered through the service layer. That makes it readable in one screen, diffable in review, and testable as a table of inputs and expected decisions — which is what `test/policy.test.js` does.
- **Row-level vs endpoint-level authorization**: checking "can this role hit this endpoint" is necessary but not sufficient — an agent hitting `GET /api/tickets/:id` is the right endpoint for their role, but the wrong ticket (someone else's team) is still a data leak if the row itself isn't checked. Every read/write here checks the actual ticket, not just the route — except the list endpoint, which scopes by query instead of a per-row `decide` call (see "How it works here" and "What this toy skips"); that is exactly the row-level-vs-endpoint-level distinction this bullet is naming, applied to this app's one collection endpoint.
- **The confused-deputy problem**: worth stating the way Norm Hardy did in 1988, because the popular retelling drifts. His deputy was a compiler that users could invoke and that also held a *home files license* letting it write its own statistics file. A user passed it the billing file's name as the destination for debugging output; the compiler passed the name to the operating system, which saw the compiler's license and allowed the write; the billing data was destroyed. Hardy's diagnosis: "the compiler runs with authority stemming from two sources," it serves two masters, and "the compiler had no way of expressing these intents" — nothing in the request said *under which authority* the write was being made. The root cause is that designation (a file name) is separate from authority (an ambient license), and his fix is capabilities, which bundle the two so that the object handle both identifies the target and confers the right to touch it. In this app the closest analogue is that `decide` is always handed the *loaded resource*, not just the id the caller typed, so a ticket id alone confers nothing — the decision is made about the object, and the caller's designation cannot borrow the process's ambient database access. It is only an analogue: `x-user-id` means the caller still supplies the identity the whole decision is built on, so this app does not actually close the gap, it just puts the check somewhere a real credential could be dropped in.

## Standard practice

- One enforcement point per action, in the service layer, never the controller — a controller-level role check is easy to forget on the next endpoint and impossible to audit as a single list. OWASP's authorization cheat sheet puts the same rule as "validate permissions on every request," regardless of where the request came from.
- Decisions carry a reason and a ruleId, never a bare boolean — a system that says "no" without saying which rule fired is not debuggable in production and not auditable after the fact.
- Default deny — an unanticipated action, resource, or role must fail closed, not open. This is OWASP's "deny by default" and Cedar's implicit deny; it is the one part of the combining behaviour that everybody agrees on.
- Deny-overrides — safety rules (delete bans, closed-ticket guards) must be able to override broad permits without the permit's author having to know about every future deny rule. Pick this deliberately and write down that you picked it: XACML would let you choose otherwise, and a reader who has only seen XACML cannot assume it from the code.
- Keep the 403 body generic and put the reason only in the server log — telling an unauthorized caller exactly which rule and attribute blocked them hands them a map for finding a path around it.
- Test the policy set as a truth table — one test per rule interaction (default deny, deny-overrides, each role boundary), not just end-to-end HTTP happy paths.

## What this toy skips

- Row-level authorization on `GET /api/tickets`: it filters the query by role instead of running every candidate row through `decide`. That is faster and matches how real apps scope collection queries, but it means the list endpoint's access boundary lives in `list()`'s filter logic, not in the policy engine, so it is not covered by the same audit trail as the per-ticket checks.
- Role hierarchies and separation of duty — the two features beyond core RBAC that the ANSI standard actually specifies. `admin` here is not a superset of `agent` by construction, it just happens to have a wildcard rule.
- Environment conditions: `context` is threaded through every call and is always `{}`, so the "and, in some cases, environment conditions" half of NIST's ABAC definition is unexercised.
- Delegation, impersonation, or "act as" flows.
- Policy versioning, staged rollout, or a UI/API for editing `policies.js` without a deploy.
- Caching decisions — every request re-evaluates the full rule set, which is fine at this scale and wrong at high volume.
- Obligations (e.g., "permit, but redact these fields") — decisions here are effect-only, not permit-with-conditions. Note that the one thing this app does that *looks* like an obligation, redacting `moderation.terms` for non-agents, is hand-written in the controller (`viewModeratable`, `src/controllers/tickets.js:7`) and the policy engine knows nothing about it.
- What OPA/Cedar/Casbin give you over this, stated concretely rather than as a gesture:
  - A declarative policy language independent of the host program, so policies can be authored, versioned and reviewed outside a code deploy — and, unlike a JavaScript `condition` closure, cannot reach out to the network or loop forever.
  - Analysis rather than only testing. Cedar is built by what AWS calls verification-guided development: the authorization engine and validator are modeled in Dafny and properties are machine-proved — including that permission is granted only by an explicit `permit` and never by default, and that an applicable `forbid` always wins — with the production Rust implementation tied back to the model by differential random testing. A hand-rolled `decide` gets whatever its unit tests happen to cover.
  - Partial evaluation. OPA can be given a policy plus the parts of the input it knows (the caller) while leaving the database columns unknown, and compile what remains into a filter — literally a SQL `WHERE` clause — that is pushed into the query. That is exactly the transformation `list()` does by hand here, which is why `list()`'s scoping drifts out of the policy set so easily.
  - A separate decision service, so PDP and PEP can be scaled, deployed and audited independently of the application.
  This engine is a teaching-sized version of the same shape, wired directly into the process.

## Try it

```
curl -s -X POST http://localhost:5001/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"rae@tickets.test","password":"demo1234"}'

curl -s -X POST http://localhost:5001/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"sam@tickets.test","password":"demo1234"}'

curl -s -X POST http://localhost:5001/api/tickets -H 'Content-Type: application/json' \
  -H 'x-user-id: <sam id>' -d '{"title":"t","body":"b","priority":"normal"}'

curl -s http://localhost:5001/api/tickets/<ticket id from above> -H 'x-user-id: <rae id>'
```

The last call returns 403 `{"error":"forbidden"}` — rae is a reporter and this ticket belongs to sam. The server console shows the line the caller does not get: `authz denied action=ticket:read ruleId=null reason=default deny: no rule matched the request`.

## Further reading

Primary sources for the models and vocabulary above, each checked against the claim it is cited for.

- [NIST, Role Based Access Control project](https://csrc.nist.gov/projects/role-based-access-control) — the Ferraiolo-Kuhn lineage, the unified NIST model, and the pointer to the current standard (ANSI INCITS 359-2004, revised as INCITS 359-2012). Start here before quoting anyone on "what RBAC formally is."
- [NIST SP 800-162, Guide to Attribute Based Access Control (ABAC) Definition and Considerations](https://nvlpubs.nist.gov/nistpubs/specialpublications/NIST.SP.800-162.pdf) — the definition this README uses, plus a long and honest chapter on the operational cost of ABAC (attribute sourcing, provenance, and governance) that policy-engine write-ups routinely skip.
- [OASIS, eXtensible Access Control Markup Language (XACML) Version 3.0](https://docs.oasis-open.org/xacml/3.0/xacml-3.0-core-spec-os-en.html) — the source of PDP/PEP/PIP/PAP and of the combining algorithms. Read the glossary (§1.1.1, "Preferred terms") and the combining-algorithm appendix (Appendix C, normative) even if you never write XACML; they are the shared vocabulary everyone else borrows.
- [Pang et al., Zanzibar: Google's Consistent, Global Authorization System, USENIX ATC '19](https://www.usenix.org/conference/atc19/presentation/pang) — the ReBAC reference design: relation tuples, usersets, namespace rewrite rules, and the zookie consistency protocol, with production latency and availability numbers over three years.
- [Cedar policy syntax: permit, forbid, and how they combine](https://docs.cedarpolicy.com/policies/syntax-policy.html) — the shortest correct statement of a fixed forbid-overrides-permit combiner with implicit deny; the counterpoint to XACML's selectable algorithms.
- [Amazon Science, How we built Cedar with automated reasoning and differential testing](https://www.amazon.science/blog/how-we-built-cedar-with-automated-reasoning-and-differential-testing) — what "formally verified authorization" actually means in practice: which properties were proved, in which prover, and how the proved model is tied to shipped code.
- [Open Policy Agent, Data Filtering with OPA](https://www.openpolicyagent.org/docs/filtering) — partial evaluation turning a policy into a SQL `WHERE` clause. This is the principled version of what `list()` does by hand, and the best argument for a policy engine over a hand-rolled one.
- [Open Policy Agent, Policy Language](https://www.openpolicyagent.org/docs/policy-language) — Rego, and the reason it has no built-in permit/deny combiner: complete rules that disagree are an error, not a conflict to resolve.
- [Norm Hardy, The Confused Deputy (or why capabilities might have been invented), ACM SIGOPS OSR 22(4), 1988](https://web.cs.wpi.edu/~cs557/f14/papers/confused_deputy-hardy.pdf) — three pages, and the only version of this story worth citing. Everything the term is used for today is a restatement of "authority stemming from two sources."
- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) — the practitioner checklist: deny by default, check on every request, server side only, and a blunt recommendation to prefer ABAC/ReBAC over role checks for fine-grained decisions.
