# Transactional outbox

## What this is

The topic this app exists for. `POST /api/transfers` has to both write a transfer and tell the outside world it happened — and a database write plus an HTTP call is not one atomic operation. Write the transfer first and the notification can be lost (the process crashes between the two); notify first and you can announce a transfer that never actually commits. No retry logic fixes this, because the failure is *between* two independent systems with no shared transaction. The transactional outbox pattern sidesteps the problem instead of solving it: write the transfer and a row describing "notify about this" in the *same* database transaction, so they succeed or fail together by construction, and let a separate process deliver that row later, independently, with its own retry logic.

## How it works here

**The write.** `services/transfers.js`'s `createTransfer` (`src/services/transfers.js:25-47`) inserts the transfer, the outbox row (`outboxRepo.create`, `src/services/transfers.js:30-35` — placed right after the transfer row and *before* the entries; statement order inside one transaction has no bearing on atomicity, the placement only lets the rollback test below fail a statement *after* the outbox insert has already run and prove the outbox row rolls back with everything else), the two entries, and the balance dual-write, all inside one `withTransaction` call (`src/db.js:8-25`). If anything in that block throws — a foreign-key violation on a bad account id, a unique-violation on a repeated `reference`, anything — the whole transaction rolls back, and the outbox row rolls back with it. `test/outbox.test.js` proves this is genuinely one transaction, not just a coincidence of what a rollback happens to undo: it asserts `SELECT xmin FROM transfers` equals `SELECT xmin FROM outbox` for a committed transfer (Postgres's `xmin` system column is the id of the transaction that last wrote a row version — two rows sharing it were written by the same transaction), and separately asserts the `outbox` table is empty after a transfer that fails *after* the outbox insert already ran.

**The relay.** `relayOnce` (`src/outbox/relay.js:37-51`) is one function, not a `setInterval` that only exists in production — `index.js:14-19` is the only place that wires it into a timer, and only when `OUTBOX_TARGET_URL` is configured, so every test drives `relayOnce` directly against a real `node:http` fake upstream. It has two phases, deliberately not one transaction spanning both: `claimBatch` (`relay.js:18-35`) opens a transaction, runs `outboxRepo.claimUnpublished` (`src/repositories/outbox.js:9-20`):

```sql
SELECT id, aggregate, aggregate_id, type, payload, attempts
FROM outbox
WHERE published_at IS NULL AND dead_lettered_at IS NULL AND attempts < $1
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT $2
```

and *commits immediately* — the claimed rows' locks are released the instant that transaction ends. Only then does `relayOnce` iterate the claimed rows and call `deliver` (`relay.js:3-11` — a plain `fetch` with `AbortSignal.timeout(2000)`) against each one, entirely outside any transaction, marking each published (`outboxRepo.markPublished`) or recording the failure (`outboxRepo.recordFailure`, or `outboxRepo.deadLetter` once `attempts` would reach `maxAttempts`) as a standalone statement on the pool once its own delivery attempt settles. This is a deliberate tradeoff: an earlier version held one transaction open across the whole batch's HTTP calls, which meant a slow or unavailable upstream pinned a database connection and every claimed row's lock for up to `batchSize × timeout`. Splitting claim-and-commit from deliver avoids that, at the cost of the row no longer being "reserved" once claimed — see At-least-once below and What this toy skips for what that costs. `backoffMs(attempts, options)` (`relay.js:13-16`) computes `random() * min(cap, base * 2 ** attempts)` — full jitter — and is exercised directly as a pure function in its own test with an injected `random`; nothing in this app currently calls it (see What this toy skips).

**The poll loop.** `index.js:14-19` only exists when `OUTBOX_TARGET_URL` is set, and only wraps `relayOnce` in a `setInterval` — but a bare `setInterval` alone is not enough once claim-then-commit is in the picture (see the core concepts below for why), so it wraps `relayOnce` in `createGuardedPoll` (`relay.js:53-66`) first: a plain closed-over `running` flag that makes a tick that fires while the previous one is still in flight a no-op, clears the flag in a `finally` (so a thrown error can never wedge it stuck), and reports errors through an injected `onError` rather than making every caller remember its own `.catch`. `test/poll.test.js` drives the guard directly with fake, hand-resolved promises (no real timers, no network) to prove all three properties; `test/outbox.test.js` then reproduces the exact failure this exists to prevent against a real slow upstream and the real `relayOnce`.

## The core concepts

- **Dual-write across two different systems cannot be made atomic after the fact.** A database transaction and an HTTP call are governed by two different failure models — the database can guarantee its own commit is atomic, but nothing can make "commit the database write" and "the HTTP call succeeded" atomic *with each other*, because there is no shared coordinator between them (that is literally what a distributed transaction protocol like two-phase commit exists to attempt, at a cost most systems aren't willing to pay). The outbox pattern doesn't solve this — it routes around it, by turning "notify the outside world" into "write one more row in the same database transaction," which the database's own atomicity already covers for free.
- **`FOR UPDATE SKIP LOCKED` is the single most useful Postgres feature most engineers have never used — and the property it buys you is non-blocking, not deduplication.** Plain `FOR UPDATE` also prevents two workers from claiming the same row: the second one simply *blocks* until the first's transaction ends, then claims whatever is left. That's correct, but it serializes every worker behind whichever one got there first, no matter how many workers you run — which defeats the entire point of having several. `test/outbox.test.js` has two tests for this, because a test that only checks "no row was delivered twice" can't tell `SKIP LOCKED` apart from plain `FOR UPDATE` (both give you that). One test claims three of six outbox rows in a transaction it deliberately holds open, fires a second claim while those locks are still held, and asserts the two claims return disjoint rows — the claim-deduplication property both locking modes share *while the first claim's transaction is open*; it is not a cross-process never-delivered-twice guarantee, which the claim-then-commit design below deliberately gives up. The other holds one row locked in an open transaction from a separate connection and asserts `claimUnpublished` still returns the *other* rows in well under a second — the property only `SKIP LOCKED` has; with plain `FOR UPDATE` that same call blocks for as long as the lock is held (verified directly: swapping in plain `FOR UPDATE` made that specific test time out).
- **Polling relay versus change-data-capture, and the tradeoff.** This relay polls: it periodically asks "any unpublished rows?" which is simple, needs nothing beyond the database this app already has, but means detection latency is bounded by the poll interval and every poll that finds nothing is a wasted round trip. Log-based CDC (Debezium reading Postgres's own logical replication stream is the standard example) instead taps the database's write-ahead log directly and pushes a change the moment it's committed, with no polling delay and no wasted queries against an empty table — at the cost of running and operating an entirely separate piece of infrastructure that understands the WAL format. Polling is the right default until the added latency or query load actually hurts; CDC is what you reach for once it does.
- **At-least-once is the guarantee — not exactly-once — and pretending otherwise is the lie this pattern exists to expose.** `test/outbox.test.js`'s crash-duplicate test proves this rather than asserting around it, and does so honestly given how `relayOnce` is actually built: it calls `claimBatch` directly (a real claim, really committed), calls `deliver` directly against the fake upstream (a real delivery, really received) — and then simply never calls `markPublished`, exactly modeling a process that crashes at that instant. The row is exactly as unpublished as it was before, so the next real `relayOnce` run claims and delivers it again. The test asserts the duplicate happens. There is no version of a polling relay (or, for that matter, a CDC-based one) that can close this window completely, because "deliver the message" and "record that it was delivered" are still two separate operations even once the *original* dual-write problem is solved — you've moved the seam, not removed it. This is why every message here carries a stable outbox row id: the guarantee this system provides is "you will receive this at least once," and the consumer's own idempotency (the same `mern-shop/server/src/idempotency/README.md` treatment referenced from `src/ledger/README.md`) is what turns "at least once" into "effectively exactly once" from the consumer's point of view. The relay cannot provide that guarantee; only a consumer that dedupes on the message id can.
- **Holding a transaction open across delivery was serializing your workers — and removing it removed that serialization too.** This is the honest lesson of the claim-then-commit redesign, not a footnote: the earlier one-transaction-per-batch version was slow under a bad upstream, but that same held transaction was *also* what made a claimed row genuinely unclaimable by anyone else until the claimer finished with it — every concurrent `relayOnce` (and every later poll tick) really did wait behind the lock. Committing the claim immediately fixes the connection-pinning problem completely, but it throws away that side effect along with it: the instant `claimBatch` commits, a claimed row is fully "unpublished" again — from the database's point of view, indistinguishable from a row nobody has touched — whether or not delivery has even started. A second claimer (another worker, or the *same* poll loop's next tick firing before the first finished) can claim and redeliver it before the first delivery attempt is even done, not only after a full crash. Reproduced directly: two `relayOnce` calls staggered 150ms apart against a 400ms-slow upstream both deliver the same row (`test/outbox.test.js`). With the app's own defaults (`batchSize` 10, a 2s per-row timeout), one slow batch can run up to ~20 seconds while further ticks of a bare `setInterval(pollMs=2000)` keep firing — so this isn't a rare crash-window edge case, it is a routine consequence of a slow upstream under this app's own configuration. `createGuardedPoll` (above) closes the *poll-loop* half of that gap — a tick never overlaps its predecessor — but it does nothing for two genuinely concurrent workers, which is exactly the scenario the competing-consumers test already accepts as a duplicate risk. Real queueing systems close the general gap with a *visibility timeout*: claiming a row also stamps it with a lease — "invisible to other claimers until this time" — extended or cleared once the claimer finishes. This schema has no such column (no `claimed_at`, no `visible_after`), so nothing here leases a row at all. None of this is a bug to fix quietly; it's why at-least-once was always the real guarantee, and why the consumer-side idempotency described above (and in `mern-shop/server/src/idempotency/README.md`) is not an optional nicety layered on top — it is the thing actually keeping this system correct once you know how routinely a duplicate can happen.
- **Ordering: per-aggregate is cheap, global is expensive.** Claiming `ORDER BY id` and processing claimed rows in that order gives per-aggregate ordering almost for free here, because every row for a given transfer is inserted together and ids are monotonic — but two different relay workers running concurrently, each claiming a different batch, can still deliver two *different* aggregates' messages in an order that doesn't match global insertion order. Guaranteeing a single global order across all aggregates would mean going back to exactly the one-worker-at-a-time serialization `SKIP LOCKED` exists to avoid — ordering and competing-consumer throughput are in direct tension, and this app deliberately keeps the throughput.
- **Poison messages and dead-letter queues.** A row whose delivery will never succeed (a permanently malformed payload, a permanently-down downstream) would otherwise be reclaimed by every relay poll forever, forever failing and forever blocking nothing else (since `SKIP LOCKED` already lets other rows through) but forever costing a wasted attempt. `deadLetter` (`src/repositories/outbox.js:31-36`) stops that once `attempts` reaches `maxAttempts`: the row is marked with `dead_lettered_at` and excluded from `claimUnpublished`'s `WHERE` clause from then on, so it stops being retried — `test/outbox.test.js`'s dead-letter test proves a bad row parking this way doesn't block a later, healthy row from still delivering in the same relay run.
- **Backoff with full jitter, and why the jitter matters.** Exponential backoff alone (`base * 2^attempts`) fixes the "retry immediately, forever, in lockstep" problem, but if many rows fail at the same moment, they all compute the *same* delay and all retry at the same moment again — a synchronized thundering herd, just delayed. Full jitter (`random() * min(cap, base * 2^attempts)`, `relay.js:13-16`) spreads that same population of retries out across the whole delay window instead of at its one endpoint, which is what actually reduces contention on the recovering downstream rather than merely postponing it.
- **Outbox growth and archival, and the inbox pattern as the mirror image.** A table that only ever gains rows needs an eventual archival or deletion strategy for published rows (this app never implements one — see What this toy skips). The **inbox** pattern is the same idea facing the other direction: instead of (or in addition to) the *sender* keeping an outbox to guarantee delivery, the *consumer* keeps an inbox table recording message ids it has already processed, so a redelivered message (which, per at-least-once above, will happen) can be detected and skipped by the consumer itself — the natural place to put the "consumer's own idempotency" this README keeps pointing at.

## Standard practice

- Write the "notify" intent in the same transaction as the business write it describes — never sequence a database commit and an external call and hope both succeed.
- Use `SKIP LOCKED` for any table multiple competing workers poll from; never let workers serialize behind row locks they don't need to wait for.
- Give every relayed message a stable, consumer-visible id and document at-least-once as the guarantee — never claim exactly-once when the mechanism can't provide it.
- Cap retries and dead-letter what exceeds the cap, so one permanently-failing message can never block the rows behind it.
- Always jitter a backoff; a synchronized retry storm is barely better than no backoff at all.
- Guard any `setInterval`-driven poll loop against overlapping ticks — a bare interval assumes the previous tick always finishes first, which a slow dependency will eventually violate.

## What this toy skips

- No archival or deletion of published outbox rows — the table only grows in this app. A production system typically deletes or moves rows some time after `published_at`, on a schedule separate from the relay itself.
- No `next_attempt_at` or lease/visibility-timeout column at all (see the claim-then-commit tradeoff above), so `backoffMs`'s computed delay is not wired into anything — nothing in this app calls it outside its own unit test. It's exercised as a correct, tested pure function so the formula itself is proven, but a production relay would persist a next-eligible-retry time (and a claim lease) per row and filter both in `claimUnpublished`'s `WHERE` clause.
- No inbox table on the consumer side — this app is only the producer/relay half of the pattern. The fake upstream in tests is a bare `node:http` server that just records what it received.
- No change-data-capture alternative actually implemented — CDC is named and scoped in the core concepts above, but this relay only ever polls.
- No metrics/alerting on outbox depth or dead-letter count — a real operator would want to know when unpublished rows are accumulating faster than the relay drains them, or when something is landing in the dead-letter state.

## In the real world (AWS / GCP)

- **The polling relay is usually the part you replace first, with CDC.** On AWS the standard stack is **Debezium on MSK Connect** (or DMS for coarser replication) tailing the RDS/Aurora Postgres WAL and publishing each committed outbox row to Kafka/EventBridge — zero poll latency, no query load on an empty table. On GCP, **Datastream** replicates Cloud SQL/AlloyDB changes into its supported destinations — BigQuery or Cloud Storage — while landing outbox events on Pub/Sub means running Debezium yourself (on a GKE-run Kafka Connect). The transactional write half of the pattern — entity + outbox row in one transaction — is unchanged; only the relay's transport changes.
- **Some databases make the outbox table itself unnecessary.** **DynamoDB Streams** and **Spanner change streams** are a built-in feed of committed writes — the database ships its own CDC, so "write the intent in the same transaction" is free because the write *is* the intent. (Firestore has no change-stream product; its equivalents are realtime listeners and Eventarc triggers.) Be precise about the guarantee: DynamoDB Streams puts each record in the stream **exactly once**, ordered per item — stronger than at-least-once; the at-least-once caveat belongs to consumption, where a Lambda reading the stream can process the same batch more than once. The price is you publish the raw row change, not a purpose-shaped event, so most teams still keep an outbox-shaped item to control the event contract.
- **The delivery target stops being one URL.** In production the relay publishes to a bus — **EventBridge**/**SNS** on AWS, **Pub/Sub** on GCP — and the bus owns fan-out, retry with backoff, and dead-letter queues per consumer. That moves this README's `backoffMs`, `maxAttempts`, and dead-letter logic out of your code and into subscription config, which is exactly where you want an operator tuning it.
- **What never moves: at-least-once and consumer idempotency.** EventBridge, SNS, Pub/Sub, Kafka — every one of them documents at-least-once delivery. The message id this relay stamps on every payload, and the consumer-side dedupe it enables, is the portable half of the pattern; carry it to whichever transport you land on.
- **The lease this schema is missing is a checkbox there.** SQS's visibility timeout and Pub/Sub's ack deadline are the `visible_after` column this outbox deliberately lacks — moving to a managed queue is also how most teams get the claim-lease behaviour without building it.

## Try it

Requires the app running against the real `ledger` database, with `OUTBOX_TARGET_URL` pointed at something that will actually receive the POST. The snippet below is a one-route `node:http` server that just logs whatever it receives:

```js
import http from 'node:http'
http.createServer((req, res) => {
  let body = ''
  req.on('data', (chunk) => { body += chunk })
  req.on('end', () => { console.log('received', body); res.writeHead(200); res.end() })
}).listen(4700, '127.0.0.1', () => console.log('fake outbox target on 4700'))
```

```bash
node fake-target.js &
echo "OUTBOX_TARGET_URL=http://127.0.0.1:4700" >> .env
npm run dev
curl -s -X POST http://localhost:5002/api/transfers -H 'Content-Type: application/json' -d '{"reference":"outbox-demo-1","fromAccountId":1,"toAccountId":2,"amountMinor":250}'
```

Within `OUTBOX_POLL_MS` (default 2000ms), the fake target's log line will show the outbox row's payload.

- [microservices.io — Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html) — Chris Richardson's canonical writeup of this exact pattern, including the polling-publisher versus transaction-log-tailing tradeoff this README's core concepts summarize.
- [PostgreSQL documentation — `SELECT` (locking clauses)](https://www.postgresql.org/docs/current/sql-select.html) — the `FOR UPDATE ... SKIP LOCKED` clause directly: "skipping locked rows provides an inconsistent view of the data... but can be used to avoid lock contention with multiple consumers accessing a queue-like table," which is precisely this relay's use case.
- [AWS Architecture Blog — Exponential Backoff and Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) — the "full jitter" formula this relay's `backoffMs` implements verbatim, and the measured contention reduction it produces over plain exponential backoff.
- [PostgreSQL documentation — Logical Decoding](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html) — how a tool like Debezium taps Postgres's write-ahead log directly, as the change-data-capture alternative to this relay's polling.
- [microservices.io — Transaction log tailing](https://microservices.io/patterns/data/transaction-log-tailing.html) — the CDC relay stated as a pattern rather than a product, and worth reading for its drawbacks section: it names "avoiding duplicate publishing" as a problem you still own, which is the same at-least-once conclusion this README reaches from the polling side.
- [Debezium — Reliable Microservices Data Exchange With the Outbox Pattern](https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/) — the practical write-up from the project most people actually run for log tailing. Read it for the event-router mechanics and for the argument that a service should only ever write to its own database, which is the principle this whole pattern is an application of.
- [Tyler Treat — You Cannot Have Exactly-Once Delivery](https://bravenewgeek.com/you-cannot-have-exactly-once-delivery/) — the precise version of the claim this README's at-least-once section makes. The distinction to carry away is that exactly-once *delivery* is an impossibility result (FLP, Two Generals), while exactly-once *effects* are routine — via at-least-once plus a deduplicating consumer.
- [Amazon SQS — Visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html) — the lease this schema does not have, in the system that made it standard: a received message "becomes temporarily invisible to other consumers", default 30 seconds, extendable in flight, 12-hour ceiling. Read it beside the claim-then-commit tradeoff above; it is exactly the column (`visible_after`) this outbox is missing, and SQS is honest that even with it, at-least-once is still the guarantee.
- [Cybertec — `SKIP LOCKED`, one of my favourite PostgreSQL 9.5 features](https://www.cybertec-postgresql.com/en/skip-locked-one-of-my-favorite-9-5-features/) — a short worked demonstration of the difference this README asserts, with two sessions side by side, if you would rather see the blocking-versus-skipping behaviour than read the reference-manual sentence about it.
