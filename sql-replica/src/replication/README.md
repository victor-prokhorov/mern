# Replication and read-after-write consistency

## What this is

A simulation of what a primary/replica database topology feels like from application code, and the small set of routing tricks that keep it correct. There is exactly one physical Postgres here — the same `mern-postgres` container every other SQL app uses — playing two logical roles: a **primary** that takes every write and can serve a strongly-consistent read, and one or more **replicas** that serve reads *as of a lagging position* and therefore hand back stale data for a window after each write. Lag is injectable, the clock is injectable, and both are frozen in the tests, so every "the replica is behind by exactly this much" claim is deterministic rather than a race you hope to catch.

Be candid about what this is and is not. This app models the **observable behaviour** of asynchronous replication — bounded staleness, read-your-writes violations, non-monotonic reads across replicas — and the application-side fixes for each. It does **not** stream WAL, run a second `postgres` process, or replay physical/logical changes over a replication slot. There is no network between primary and replica because there is no second server; "the replica hasn't got the write yet" is modelled by a visibility rule over an append-only log, not by bytes in flight. The section [In the real world](#in-the-real-world-aws--gcp) is explicit about every place the simulation and real replication diverge, because the divergences are exactly the things worth knowing.

## How it works here

**The replication log.** Every write appends a row to `changes` (`src/repositories/changes.js:5-16`) — an append-only table where each row carries a globally monotonic `version` (from a single Postgres `SEQUENCE`, `src/migrations/002_create_changes.sql`) and a `written_at` timestamp stamped from the injected clock, not from the database's own `now()`. Because writes are serialized through the primary, `version` order and `written_at` order always agree. A document is never updated in place; a new value for `(account_id, doc_key)` is a new `changes` row with a higher version, and the old row stays. That is what lets a replica reconstruct an *earlier* state — the whole point of the exercise — the same way real MVCC and WAL replay let a lagging replica serve a consistent older snapshot rather than a torn one. It is also the same append-only shape the ledger uses for `entries` (see [`../../../sql-ledger/src/ledger/README.md`](../../../sql-ledger/src/ledger/README.md)): the history *is* the system of record, and the current value is a query over it.

**Replica position.** Each replica has a replay position, `applied_through`, stored in `replica_state` (`src/migrations/003_create_replica_state.sql`) and advanced by `tick(env)` (`src/replication/tick.js:5-22`). A tick sets a replica's position to the highest version whose `written_at <= now - lagMs` — the newest change that is *older than the lag* — using `GREATEST` so the stored position can only ever move forward (`src/repositories/replicaState.js:14-23`). That last property matters: a single replica's replay position never goes backwards, exactly like real WAL replay never un-applies a record. In the running app a background loop calls `tick` every `TICK_MS` (`src/index.js`); in tests you call it explicitly after advancing the clock, which is what makes the staleness window a number you can assert on.

**Read routing.** `readDocument` (`src/replication/router.js:47-81`) is the centrepiece. It decides between primary and replica in this order:

1. `consistency: 'strong'` → always the primary (`src/replication/router.js:59`). This is the escape hatch for a read that cannot tolerate any staleness — a balance check before an overdraft decision, say. Reads to a replica are the default because most reads *can* tolerate it.
2. Otherwise, if a **sticky-primary window** is active — the session wrote within the last `stickyMs` (`withinStickyWindow`, `src/replication/router.js:6-8`) — route to the primary. This is read-your-writes fix (a).
3. Otherwise pick a replica with `pickReplica` (`src/replication/router.js:10-21`), a round-robin over the topology that **skips any replica whose `applied_through` is below the required version** (`requiredVersion`, `src/replication/router.js:23-28`). The required version is the max of a client-supplied write-position `token` and, if the read is `pinned`, the highest version this session has already seen. If some replica qualifies, the read is served from it, as of its `applied_through`. If none does, the router **falls back to the primary** rather than serve a read that would violate the caller's guarantee.

A write (`writeDocument`, `src/replication/router.js:39-45`) always goes to the primary, appends to the log, and returns its `version` — that returned version is the **write-position token** the client can carry into a later read. The session object (`src/replication/session.js`) records the last write (time and version, for the sticky window and token) and the highest version read (`seenVersion`, for monotonic pinning).

**The injected clock.** `createClock(startMs)` (`src/replication/clock.js:1-8`) is a plain mutable clock — `now()`, `set(ms)`, `advance(ms)` — that the tests drive directly, so "5 seconds have passed" is a function call, not a `setTimeout`. The running app uses `systemClock` (`src/replication/clock.js:10-14`) instead, which is real wall-clock time. This mirrors how `sql-scheduler` injects `now` so its cadence maths is testable ([`../../../sql-scheduler/src/scheduler/README.md`](../../../sql-scheduler/src/scheduler/README.md)) — the difference is that the scheduler reads `now` from the database (`SELECT now()`), while here the clock also *stamps* every write's `written_at`, so that lag arithmetic (`written_at <= now - lagMs`) is entirely deterministic and doesn't depend on how long the test took to run.

## The core concepts

- **Replication lag is a duration, and staleness is bounded by it.** A replica that is "5 seconds behind" reflects every write that committed more than 5 seconds ago and no write newer than that. Turned into an invariant: after a tick at time `now`, a replica with lag `L` has applied every change with `written_at <= now - L`, so the oldest a replica read can ever be is `L` — never more. `test/replication.test.js` asserts both halves: everything older than `lagMs` is visible, nothing younger is, and a write becomes visible the instant it crosses the `lagMs` boundary. Bounded staleness is the *only* consistency a naive read replica gives you for free; every stronger guarantee below is something the application adds on top.
- **"Read the replica right after a write" is the bug, and it is why it breaks checkout.** The classic incident: a user updates their address, the next page re-reads it from a replica that hasn't caught up, and shows the old address — or worse, an order total is written to the primary and immediately re-read from a replica as the pre-write value, and the charge is wrong. The STALE test reproduces exactly this: write `v1`, read the replica, get `v0` back with `fresh: false`, while the primary has `v1`. Nothing is broken in the database — the replica is behaving correctly by being behind. The bug is in *routing a read that needed the primary to a replica*.
- **Read-your-writes: a session must see its own writes, even if nobody else's yet.** Two independent fixes, both here, and they trade off differently:
  - **Sticky-primary window (fix a).** After a write, pin *this session's* reads to the primary for `stickyMs`. Dead simple, needs no cooperation from the read call site beyond "use my session", and it is what most web frameworks reach for. The cost: every read in the window hits the primary even when the replica would have been fine, and if `stickyMs` is shorter than real lag you still get a stale read at the edge, while if it is longer you send avoidable load to the primary. It is a *time-based guess* at how long catch-up takes.
  - **Write-position token (fix b).** The write returns its log position; the client carries that token into later reads; a replica read is allowed only from a replica that has actually applied through that position, otherwise it falls back to the primary. This is exact rather than a guess — it waits for the *actual* catch-up, not an estimated duration — at the cost of threading a token through your API (a header, a cookie, a field). This is the same idea as Aurora's replica-read consistency modes and MySQL's `MASTER_POS_WAIT`/GTID-based `WAIT_FOR_EXECUTED_GTID_SET`: the client says "don't answer until you've replayed at least up to here."
- **Monotonic reads: time must not run backwards for one reader.** Read-your-writes is about seeing your *own* writes; monotonic reads is the weaker-sounding but distinct promise that once you have seen a value, you never later see an *older* one. It breaks not on one replica (a single replica's position only moves forward here) but across *two* replicas of different lag behind a load balancer: read one that's caught up (version 2), then get load-balanced to one that's further behind (version 1), and the world appears to move backwards. The unpinned test shows exactly this regression; the pinned test fixes it by remembering the highest version the session has seen and refusing any replica behind it — the same `requiredVersion` machinery as the token, sourced from `seenVersion` instead of an explicit token. Real systems solve this with sticky routing (a session always hits the same replica) or session-consistency tokens; pinning is the token version.
- **CAP is the wrong frame for this; PACELC is the right one.** CAP says: when the network **P**artitions, you choose **C**onsistency or **A**vailability. True but narrow — partitions are rare, and CAP says nothing about the normal case. **PACELC** (Abadi) extends it: *if Partition, then C-or-A; Else, Latency-or-Consistency.* The "else" is where this whole app lives. There is no partition in the STALE test — the replica is up, reachable, and answering — yet you still trade consistency for latency, because reading the nearby lagging replica is faster than the round-trip to the authoritative primary. A single-leader Postgres with async replicas is a **PA/EL** system in Abadi's taxonomy: during a primary-replica partition it stays available — the primary keeps accepting writes and the cut-off replica keeps serving reads that only grow staler — at the cost of linearizability. (The replica cannot accept writes, so the copies never *diverge*, but non-divergence is not CAP consistency; a genuinely PC system, like Abadi's PNUTS-in-PC-mode exemplar, refuses the affected operations instead.) In normal operation it sacrifices consistency for latency (reads may be stale). Every fix in this README is a knob for buying some of that "else-branch" consistency back, one read at a time, and paying latency (primary round-trip) or staleness (wait for catch-up) for it. That per-read choice — `strong` vs `eventual` vs token-gated — is PACELC's "L or C" made into an API parameter.
- **Bounded staleness vs. strong consistency vs. eventual.** These are points on a line, not a binary. Strong (linearizable) reads always see the latest committed write — here, the primary. Eventual consistency promises only that *if writes stop*, replicas converge — it puts no bound on how stale a read can be right now. Bounded staleness sits between: stale, but by no more than a stated amount. A read replica gives bounded staleness by default and can be upgraded per-read to strong (route to primary) or to session-consistent (token/pin) — which is why "just add a read replica" is never a whole answer; it is a menu, and the application has to order from it.
- **Why a ledger reads the primary.** The overdraft check in [`../../../sql-ledger/src/ledger/README.md`](../../../sql-ledger/src/ledger/README.md) — "read the balance, decide if a debit is allowed, write" — is exactly a read that cannot run on a lagging replica: a balance that is 5 seconds stale can approve a debit that the real balance forbids, and you have double-spent. That is the `consistency: 'strong'` path, and it is why analytics and dashboards move to replicas while the money read-modify-write stays on the primary (under a row lock, per that README). Correctness reads go to the leader; tolerant reads go to the followers; knowing which is which is the design work.

## Standard practice

- Default reads to a replica and treat the primary as the exception you opt into, not the other way round — otherwise you have bought read replicas and still send all load to the leader.
- Give every read an explicit consistency requirement (strong / read-your-writes / eventual) at the call site, and make the router honour it, rather than letting "which connection did the ORM happen to grab" decide correctness.
- For read-your-writes, prefer a write-position token when you control the client and can thread it through (it waits for the real catch-up); fall back to a sticky-primary window when you cannot, and set the window from your **measured** replication lag with headroom, never a guessed constant.
- For monotonic reads, either route a session consistently to one replica or carry a session-consistency token; do not assume a load balancer over replicas preserves order, because it does not.
- Keep read-modify-write correctness reads (balances, inventory, uniqueness checks) on the primary under a lock; only tolerant reads (lists, dashboards, search, analytics) belong on a replica.
- Monitor replication lag as a first-class signal and alert on it: every guarantee above is stated *relative to* the lag, so an unbounded lag silently turns "bounded staleness" into "eventual" and every sticky window shorter than the real lag starts failing.

## What this toy skips

- **No real replication.** There is no second Postgres, no WAL sender/receiver, no replication slot, no logical decoding. "The replica" is a visibility rule over one table in one database. A real replica can fall arbitrarily far behind under write pressure, be promoted to primary on failover, diverge and need re-seeding, or serve a *torn* read mid-apply that this model never produces. The append-only `changes` log stands in for the WAL; a genuine replica replays physical page changes or logical row events, not a tidy per-key version history.
- **Lag is a single clean number per replica.** Real lag is a distribution that spikes with write volume, vacuum, network weather, and long-running queries on the standby — which either stall WAL apply while the standby waits out the recovery conflict (`max_standby_streaming_delay`) or, with `hot_standby_feedback` on, report the standby's oldest xmin to the primary so it defers vacuum cleanup. Here `lagMs` is constant and the clock is frozen, precisely so the tests are deterministic — but that determinism is the thing least like production.
- **The replica applies only on an explicit tick.** A real replica applies continuously; the discrete `tick` is a teaching device (and matches the running app's interval loop). Between ticks the modelled position is frozen even as wall-clock time passes, which a real replica's would not be.
- **Writes cannot go to the replica, and there is no failover.** No replica promotion, no split-brain, no fencing of a demoted primary. The single genuine partition-tolerance property of a real single-leader setup — a replica physically cannot accept a write, so it cannot diverge — is true here only because there is nothing to diverge from.
- **No multi-leader or quorum model.** This is single-leader async replication only. Multi-primary conflict resolution, quorum reads/writes (Dynamo-style `R + W > N`), and CRDT convergence (touched on in [`../../../mern-tickets/server/src/concurrency/README.md`](../../../mern-tickets/server/src/concurrency/README.md)) are all out of scope.
- **Session state is per-process and in-memory.** The HTTP layer keeps sessions in a `Map` (`src/services/documents.js`), so sticky windows and pins do not survive a restart and do not span instances. A real deployment keeps the write-position token on the client (cookie/header) precisely so it survives both.
- **Bigint versions are read back as JS numbers.** The `version` sequence is small in this toy, so the position arithmetic uses `Number`; the ledger keeps `BIGINT` as a string for exactly the precision reason this app ignores (see its Try it note).

## In the real world (AWS / GCP)

- **AWS RDS/Aurora read replicas.** RDS for Postgres/MySQL gives you async read replicas behind separate endpoints; Aurora gives you a **reader endpoint** that load-balances across replicas sharing one storage volume, with lag typically in the low tens of milliseconds rather than seconds. Aurora Postgres exposes `aurora_replica_read_consistency` (`eventual` / `session` / `global`) — set it to `session` and the reader endpoint gives you read-your-writes and monotonic reads without threading a token yourself, because the engine tracks your session's write position for you. That session mode is the managed version of this app's token + pin, moved from application code down into the database. The reader endpoint load-balancing across replicas of differing lag is also exactly the monotonic-reads hazard: without `session` consistency, two consecutive reads through the reader endpoint can hit different replicas and go backwards.
- **RDS Proxy pitfalls.** RDS Proxy (and any transaction-mode pooler — see the ledger README's note on the same hazard) multiplexes many client connections over few database connections, and in doing so it can hand successive queries from one logical client to *different* backend connections and even different replicas. That breaks session-pinned consistency and any session-scoped state (advisory locks, `SET` parameters, temp tables) unless you pin the session explicitly. "We added RDS Proxy and started seeing our own writes disappear on the next read" is the read-your-writes bug reintroduced by the pooler after the application thought it had fixed it.
- **GCP Cloud SQL and AlloyDB.** Cloud SQL for Postgres offers read replicas with their own connection endpoints; you route reads to them in application code, exactly the routing this app does by hand. AlloyDB adds **read pools** — a set of replica nodes behind one endpoint that autoscale — which is Aurora's reader-endpoint shape on GCP, with the same "which node answered, and how far behind is it" question. Cross-region replicas on either cloud turn the lag from milliseconds into tens of milliseconds plus the speed of light, which is where bounded-staleness reasoning stops being pedantic.
- **"Route reads to a replica, pin after a write" in frameworks.** Rails (`ActiveRecord` automatic role switching, `connected_to`), Django (database routers), Laravel (`read`/`write` connections with `sticky: true`), and Spring (`@Transactional(readOnly = true)` plus an `AbstractRoutingDataSource`) all ship the two mechanisms in this README: send reads to a replica by default, and stick to the primary for a window after a write. Laravel's `sticky` flag *is* fix (a); it defaults the window to "the rest of the current request", which is a pragmatic, conservative version of `stickyMs`.
- **What stays app code no matter what you buy.** The managed service gives you replicas, endpoints, and sometimes a session-consistency mode. What it never decides for you: *which* reads must be strong (the ledger's balance check) versus tolerant (a dashboard); how large a staleness your product can actually show a user; whether a given read needs read-your-writes or full monotonicity; and setting and alerting on a lag budget. Aurora `session` consistency and Laravel `sticky` remove the plumbing, but the classification of every read into a consistency requirement is a domain decision that lives in your code — which is the decision this whole app exists to make visible.
- **The cousin problem: migrations.** The old/new schema overlap in [`../../../sql-ledger/src/migrations/README.md`](../../../sql-ledger/src/migrations/README.md) is the same shape as primary/replica skew: two versions of the truth coexisting for a window, and every reader has to stay correct while they do. Expand-contract makes a *schema* change safe across that window the way replica routing makes a *data* read safe across replication lag — in both, the fix is to stop pretending the window doesn't exist and instead make every step correct while it is open.

## Try it

Requires the app running against the real `replica` database (see the root `README.md` for Docker/migrate/start), on port 5007, not the test database. The default topology is one replica with `REPLICA_LAG_MS=5000` and a `STICKY_MS=5000` window; a background loop ticks the replica every `TICK_MS`.

```bash
cd sql-replica
npm install
cp .env.example .env
npm run migrate
npm run dev
```

Create an account and write a document to the primary. The write returns a `version` — that number is your write-position token:

```bash
curl -s -X POST http://localhost:5007/api/accounts -H 'Content-Type: application/json' -d '{"name":"alice"}'
curl -s -X POST http://localhost:5007/api/documents -H 'Content-Type: application/json' \
  -d '{"accountId":<alice id>,"docKey":"profile","body":"v1"}'
```

`{"source":"primary","version":1,...}`. Now read it back three ways, immediately, before the 5-second lag has elapsed:

```bash
curl -s 'http://localhost:5007/api/documents/<alice id>/profile'                       # plain: replica
curl -s 'http://localhost:5007/api/documents/<alice id>/profile?consistency=strong'    # primary
curl -s 'http://localhost:5007/api/documents/<alice id>/profile?token=1'               # token-gated
```

The plain read is routed to the replica and comes back `{"source":"replica","body":null,"fresh":false}` — the write is real but the replica has not applied it yet, so it is invisible. That is the read-after-write bug. The strong read is `{"source":"primary","body":"v1","fresh":true}`. The token read is *also* `source: primary` — the token forces the primary because no replica has yet applied through version 1. Watch the replica catch up:

```bash
curl -s http://localhost:5007/api/replication/state
# wait ~6 seconds for the background tick to advance the replica past the 5s lag
curl -s 'http://localhost:5007/api/documents/<alice id>/profile?token=1'
```

`state` shows the primary position and each replica's `appliedThrough`. Once `appliedThrough` reaches 1, the same token read flips to `{"source":"replica","body":"v1"}` — the client's guarantee is now satisfiable from the replica, so the router stops paying the primary round-trip. The sticky window behaves the same way for a session: pass `?sessionId=s1` on both the write and the reads and, for `stickyMs` after the write, `?sessionId=s1&sticky=1` reads route to the primary regardless of lag.

The deterministic, frozen-clock versions of all of this — the exact staleness boundary, monotonic reads going backwards across two replicas, and the pin that fixes them — are in `test/replication.test.js`, which is the more precise way to see the behaviour than curl against a moving wall clock.

## Further reading

- [Daniel Abadi, *Consistency Tradeoffs in Modern Distributed Database System Design* (the PACELC paper)](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf) — why CAP is not enough and the "else, latency-or-consistency" branch is where most systems actually spend their time. The single most useful frame for the choices this app turns into API parameters.
- [Kleppmann, *Designing Data-Intensive Applications*, ch. 5 (Replication)](https://dataintensive.net/) — leader-based replication, replication lag, and the three guarantees named here (read-your-writes, monotonic reads, consistent prefix) with the failure scenario for each. The book's "Problems with Replication Lag" section is this README's source material.
- [Jepsen: Consistency models](https://jepsen.io/consistency) — the map from strong (linearizable) down through bounded staleness and monotonic reads to eventual, with the precise definitions this README uses loosely. Read it to see how much finer the real lattice is than "strong vs eventual".
- [PostgreSQL documentation — Hot Standby and streaming replication](https://www.postgresql.org/docs/current/hot-standby.html) — what a real Postgres replica is: WAL sender/receiver, recovery conflicts, and why a long-running query on the standby either stalls apply until `max_standby_streaming_delay` expires or — with `hot_standby_feedback` reporting the standby's oldest xmin back to the primary — holds back vacuum on the primary. Everything this app abstracts away.
- [AWS — Aurora replica read consistency (`aurora_replica_read_consistency`)](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraPostgreSQL.BestPractices.html#AuroraPostgreSQL.BestPractices.ReadConsistency) — the managed `session`/`global` modes that are this app's token-and-pin moved into the engine, and the reader endpoint that creates the monotonic-reads hazard in the first place.
- [MySQL — `WAIT_FOR_EXECUTED_GTID_SET` / `MASTER_POS_WAIT`](https://dev.mysql.com/doc/refman/8.0/en/gtid-functions.html) — the write-position token made a first-class SQL function: block a replica read until it has replayed at least up to a given position. The exact mechanism fix (b) simulates.
- [Bailis et al., *Highly Available Transactions: Virtues and Limitations*](http://www.vldb.org/pvldb/vol7/p181-bailis.pdf) — where session guarantees (read-your-writes, monotonic reads/writes, writes-follow-reads) come from as a formal family, and which are achievable without giving up availability.

Elsewhere in this repo: [`../../../sql-ledger/src/ledger/README.md`](../../../sql-ledger/src/ledger/README.md) for why the balance read-modify-write must stay on the primary (the canonical "correctness read cannot tolerate lag" case); [`../../../sql-ledger/src/migrations/README.md`](../../../sql-ledger/src/migrations/README.md) for old/new schema overlap, the cousin of primary/replica skew; [`../../../sql-scheduler/src/scheduler/README.md`](../../../sql-scheduler/src/scheduler/README.md) for the injected-clock pattern this app borrows to make lag deterministic; and [`../../../mern-tickets/server/src/concurrency/README.md`](../../../mern-tickets/server/src/concurrency/README.md) for CRDTs, the convergence story for the multi-leader world this single-leader app deliberately avoids.
