# Idempotency keys

## What this is

A mechanism that lets a client safely retry `POST /api/orders` after a timeout or dropped connection without risking a second order. The client generates an `Idempotency-Key`, sends it on the request, and the server guarantees that every request carrying that same key returns the exact same result — the order is created at most once, no matter how many times the request is retried.

## How it works here

1. If the request carries no `Idempotency-Key` header, behaviour is completely unchanged (`middleware/idempotency.js:10-13`): the request runs exactly as it did before this feature existed. This is a deliberate choice, not an oversight — see the core concepts section for why a real money-moving endpoint usually should not leave this optional.
2. If a key is present, the middleware computes the caller's identity via an injected `userIdFrom(req)` function (`middleware/idempotency.js:14`) and a SHA-256 fingerprint of the canonicalised request body (`middleware/idempotency.js:15`, `idempotency/fingerprint.js:14-17`), then tries to **insert** — not upsert — an `in_progress` `IdempotencyKey` document, `claimedAt` defaulting to now (`middleware/idempotency.js:19`, `repositories/idempotencyKeys.js:3-5`, `models/idempotencyKey.js:10`). The compound unique index on `{ key: 1, user: 1 }` (`models/idempotencyKey.js:15`) is what makes this safe: exactly one concurrent insert for a given `(key, user)` pair can succeed, and every other one raises a MongoDB duplicate-key error (code `11000`). There is no read-then-write here — the middleware never checks "does this key already exist?" before inserting; it just inserts and lets the database's own uniqueness constraint decide who got there first, which is the same shape as `repositories/rateLimits.js:5-9`'s atomic upsert, just with `create()` instead of `findOneAndUpdate({ upsert: true })` because ownership here is first-insert-wins rather than shared-counter.
3. When the insert succeeds, the request proceeds to the real controller. The middleware patches `res.json` (`middleware/idempotency.js:53-73`) so that whatever the controller eventually sends is intercepted before it reaches the client, and — this is load-bearing, not incidental — the patched `res.json` is `async` and **awaits** the store write before ever calling the real `res.json` (`middleware/idempotency.js:59,64,72`): a status `>= 500` releases the claim by deleting the `IdempotencyKey` document (`repositories/idempotencyKeys.js:15-17`) so the same key can be claimed again; anything else — 2xx or 4xx alike — stores the exact status and body and marks the record `completed` (`repositories/idempotencyKeys.js:11-13`). Both writes are conditioned on the claim's current `epoch` matching the epoch this request was handed when it won its claim (`claimed.epoch`) — see point 4 for why that matters. The stored body is round-tripped through `JSON.parse(JSON.stringify(body))` (`middleware/idempotency.js:56`) before being written to the `Mixed` field, so a later replay reproduces byte-for-byte what `res.json` would have serialized the first time — including Mongoose documents' own `toJSON` transforms (`models/order.js:31-37` strips `fraud` and `__v`), not whatever internal shape the document happens to hold in memory. An earlier version of this code fired the store write with `.catch(() => {})` and called the real `res.json` immediately, without waiting. That is a real bug, not a hypothetical one: a replay that happened to land within the write's own latency would find the record still `in_progress` and get a spurious `409` even though the original had already succeeded — and worse, if the fire-and-forget write itself failed for any reason, the claim stayed `in_progress` for the full 24-hour TTL, so every subsequent legitimate retry got a *permanent* `409` while the order had, in fact, already been placed. That is exactly the failure this feature exists to prevent, reintroduced by not awaiting the one write that matters. If the awaited write still fails — the store itself is down, say — the middleware logs it at error level with the key, user, and status (`middleware/idempotency.js:70`) rather than swallowing it silently, and still answers the client with the real response either way; recovery from that failure is the lease, not a nested retry (see the next point). If the write instead completes but matches nothing — `released.deletedCount === 0` or `markCompleted` returns null — that means the epoch moved on since this request claimed it, logged as a warning rather than an error (`middleware/idempotency.js:61,66`): this request has been superseded, and its write correctly became a no-op instead of touching whichever newer claim now owns the key.
4. When the insert fails with `11000`, the middleware looks up the existing record for that `(key, user)` pair (`middleware/idempotency.js:25`) and checks the stored fingerprint first, before status: a mismatched fingerprint is a client bug — same key, different request — and gets `422` regardless of whether the original request is still running or already finished (`middleware/idempotency.js:30-33`). Once the fingerprint matches, `completed` replays the stored status and body verbatim with an `Idempotent-Replay: true` header (`middleware/idempotency.js:34-38`). `in_progress` is where the lease decides the outcome: `middleware/idempotency.js:39-40` computes `staleBefore = now - leaseMs` (`leaseMs` defaults to 30 seconds, `middleware/idempotency.js:5`) and compares it against the existing record's `claimedAt`. Still within the lease — `claimedAt` is newer than `staleBefore` — means someone is genuinely working on this claim *right now*, so the middleware responds `409` with `Retry-After: 1` and does not wait for it (`middleware/idempotency.js:40-44`). Past the lease means the claim is stale: the process holding it crashed, its own cleanup (`release`/`markCompleted`) failed and got silently stuck, or — the case that matters most, see the core concepts note on fencing below — it is simply still running and slower than the lease anticipated. Rather than trust that diagnosis blindly, the middleware attempts one more atomic step — `store.reclaimStale` (`middleware/idempotency.js:45`, `repositories/idempotencyKeys.js:19-25`), a `findOneAndUpdate` matching `{ key, user, status: 'in_progress', requestFingerprint, claimedAt: { $lt: staleBefore } }` that resets `claimedAt`/`expiresAt` **and increments `epoch`** — and only if that succeeds does this request take over the claim and proceed as if it had won the original insert (`middleware/idempotency.js:51`). The epoch bump is the fencing token: it is what lets the two owners' later writes (point 3) tell "am I still the current claim, or was I superseded" apart, atomically, without a second race. If the reclaim itself doesn't match — someone else reclaimed or completed it in the instant between the read and this update — the request falls back to `409` (`middleware/idempotency.js:46-49`), the same safe answer as the fresh-lease case.
5. `routes/orders.js:8` wires `requireAuth, idempotency({ userIdFrom: (req) => req.userId })` in front of `orders.place`. `userIdFrom` originally read `req.body.userId` — the only identity this app had before `../session/README.md`'s feature landed — and moved to `req.userId` (the id `requireAuth` puts on the request from a verified access token) in the same commit that closed the client-supplied-identity hole at checkout. `idempotency` itself does not care which source it is handed; it only cares that `userIdFrom(req)` names the caller correctly, whatever the current identity model is.

## The core concepts

- **At-least-once clients make retries inevitable.** A client that sends a request and never receives a response cannot distinguish "the server never got it" from "the server processed it and the reply was lost." The only two honest choices are: never retry (and leave the user stuck on a network blip), or retry and make retries safe. Idempotency keys are what makes the second choice viable for an operation — creating an order — that is not naturally safe to repeat.
- **Idempotent by nature vs. made idempotent.** RFC 9110 defines `PUT`, `DELETE`, `GET`, and `HEAD` as idempotent by nature: "the intended effect on the server of multiple identical requests ... is the same as the effect for a single such request." `POST /api/orders` is not naturally idempotent — two identical `POST`s create two orders — so idempotency here is manufactured with a client-supplied key rather than inherent to the method.
- **Fingerprinting exists so the key can't lie.** Without checking that the body matches, a client could send `Idempotency-Key: abc` with a $5 order, then reuse `abc` with a $500 order and silently get back the $5 order's result — or worse, if the second request were allowed to execute, the key would stop meaning "this exact operation" and start meaning nothing. Stripe's own docs are explicit that the idempotency layer "compares incoming parameters to those of the original request and errors if they're not the same." This implementation checks that before anything else.
- **Scoping and the leak this prevents.** The unique index is on `{ key, user }`, not `{ key }` alone. If keys were global, a client could guess or intercept another user's `Idempotency-Key` string and, on collision, receive that user's stored response — an order confirmation, its total, its customer details — as their own reply. Scoping by user turns "guess someone's key" from a data leak into a no-op: the guesser's own claim attempt for `{ key, otherUser }` simply doesn't collide with `{ key, thatUser }` at all, because the compound index treats them as entirely different documents.
- **Why 409 and not waiting.** An in-progress duplicate could, in principle, have the second request block until the first resolves and then return its result. This implementation deliberately does not: waiting ties up a server connection for however long the original request takes, turns one slow request into two, and gives no way for the caller to know how long is reasonable to wait. Responding `409 Retry-After: 1` immediately puts the decision back where it belongs — with the caller — and costs the server nothing beyond the lookup it already had to do.
- **A concurrency test cannot prove your code is atomic when the database constraint is doing the work.** This claim needed correcting mid-review, and the correction is the more useful lesson than the original claim would have been. `claim()`'s own test hammers the same `(key, user)` pair with ten concurrent calls and asserts exactly one winner (`test/idempotency.test.js`). That test passes today. It would *also* pass against a deliberately broken implementation — `findOne` first, `create()` only if nothing was found, no unique-constraint error ever caught — because the unique index on `{ key, user }` still rejects every concurrent insert past the first, whether or not the caller did a pointless read beforehand. Verified directly: that check-then-act version was hammered ten-way and fifty-way, with and without an injected delay between the read and the write, and every run still produced exactly one winner and nine `11000` errors. A concurrency test proves "the database only ever let one insert through," which is a property of the unique index, not of whichever application code happens to sit in front of it. The antipattern only becomes visible with a *sequential* probe: claim a key, let it fully commit, then claim the same key again — the correct implementation throws `11000` on the second call; the check-then-act version silently hands back the first call's own document, which is the actual bug (a second caller believing it owns a claim someone else already holds). `test/idempotency.test.js`'s "claim never silently hands a second caller the first caller's already-claimed record" is that probe, and it is the one that told the two implementations apart — confirmed by mutating `claim()` back to check-then-act and watching that specific test fail while the concurrent-hammer test kept passing. The general version: a unique constraint backing an insert makes *concurrent* correctness free, no matter how carelessly the calling code is written; it says nothing about a *sequential* correctness bug like silently treating someone else's row as your own. Test for the second kind on its own terms — a probe against already-committed state — rather than assuming heavier concurrency will eventually shake it loose.
- **Retention windows.** `expiresAt` is 24 hours from claim (`middleware/idempotency.js:4,16`), enforced by a MongoDB TTL index (`models/idempotencyKey.js:12`, `expires: 0`, meaning "expire exactly at the stored `expiresAt` moment"). This matches Stripe's own stated window — "remove keys from the system automatically after they're at least 24 hours old" — and the same caveat from `rateLimit/README.md` applies: TTL deletion is a background sweep that runs roughly once a minute, not an instant guarantee, so a key can outlive `expiresAt` by up to that sweep interval before it is physically removed. That laziness never causes incorrect behaviour, only a delay in reclaiming storage: nothing here reads a document by "is it expired," only by `(key, user)`.
- **Leases turn "release failed" into a bounded, self-healing gap instead of a silent permanent one — and introduce a new problem in the same motion.** The straightforward version of "release on 5xx" — delete the `in_progress` record when the handler fails — has an unhandled failure mode: if the delete itself throws (store outage, network blip), the record never gets removed, and the key stays claimed for the full 24-hour TTL. Every retry for that window then gets `409` while the operation that was supposed to have failed may or may not have actually happened. Catching and retrying the same delete in the error handler only moves the same failure one level down — it can fail too. A lease sidesteps the whole class of failure instead of trying to make one specific write more reliable: an `in_progress` claim is only ever trusted for `leaseMs`, so a crashed process, a failed release, or a failed markCompleted all degrade to the same bounded outcome — retries get `409` for up to 30 seconds, then the next one reclaims and actually runs. Thirty seconds is chosen to be comfortably longer than this endpoint's real latency (so a legitimately still-running request is never mistaken for abandoned) and comfortably shorter than making an impatient client wait out the full TTL. But naming a timeout does not make "still running" and "dead" distinguishable from the outside, and a lease on its own hands the *same document* to whichever request reclaims it — the original request never finds out it lost the lease and keeps running, keeps holding its own copy of the claim id, and keeps writing to it when it finishes. Built and run without the fix in the next bullet, on a stale (30s-ish) lease with a slow-but-alive original and a fast reclaimer: both handlers execute in full — this app placed two orders for one idempotency key, not one; whichever finishes last simply overwrites the store, so the stored and replayed response can describe the *wrong* execution — a caller replaying the key later gets told about an order that is not the one their own request actually triggered the creation of; and if the stale original's own response is `>= 500`, its release call deletes the *reclaimer's* now-completed record out of the store entirely, because nothing distinguishes "my claim" from "someone else's claim that reused my document" — which reopens the key for a third request to claim fresh and run a third time, with no bound on how many further requests can pile onto one key this way. Confirmed by running exactly that scenario against this code before the fencing fix landed: two executions, the stored response describing the wrong one, and a third execution after the stale owner's release. **Every lease has this problem the moment two owners can legitimately believe they hold it at once — a lease without a fence trades a wedge for silent duplication, it does not remove the failure mode, it relocates it.**
- **Fencing tokens are the standard answer, and they fix corruption, not duplication.** The fix is `epoch` (`models/idempotencyKey.js:11`): every successful claim or reclaim carries a distinct epoch (`reclaimStale`'s `$inc`, `repositories/idempotencyKeys.js:22`), and every later write is conditioned on that exact epoch still being current (`markCompleted`/`release`'s `{ _id, epoch }` filter, `repositories/idempotencyKeys.js:11-16`). A superseded owner's write then matches nothing — it is a no-op, not a corruption — because the document has already moved to a newer epoch by the time the stale owner gets around to writing it. This is the textbook fencing-token pattern from lease-based distributed systems (Chubby, GFS's file leases): a monotonically increasing token issued with every lease grant, checked by whoever the lease-holder writes to, so a client that has lost its lease without realizing it cannot make a write stick. It is worth being precise about what fencing does and does not buy back. It does not stop the double execution itself — by the time a reclaim can happen, the original request's handler is already running, and nothing here reaches into that in-flight execution to cancel it; a real fencing scheme that prevented the second half of the work would need the fence checked *inside* the side-effecting write itself (Order creation would need to carry and verify the epoch), which this app does not do. What fencing buys is that the *idempotency store* stays honest about which claim is current no matter which owner's write lands last or first: the reclaimer's completed response survives a late-arriving stale write, and a stale owner's release can never delete a claim it no longer holds. Duplication under a genuinely slow-but-alive original is a real, open gap in this design (see "what this toy skips"); silent, unbounded corruption of the store is not, once fenced.
- **A fence is only as strong as the field it checks, and adding that field to a live system is its own hazard.** `claim()` sets `epoch: 1` explicitly (`repositories/idempotencyKeys.js:4`) rather than leaning on the schema's `default: 1` (`models/idempotencyKey.js:11`) to supply it. The two look equivalent for a fresh claim — Mongoose applies the default at construction time either way — but they stop being equivalent the moment `epoch` reaches the write path as a bare JS `undefined` rather than a real number, which is exactly what happens for a document that predates the field entirely: verified directly, inserting a record with no `epoch` key at all (bypassing the schema, as a stand-in for a row written by code before this fix existed) and then calling `release(id, undefined)` deletes it unconditionally — `deletedCount: 1` — because Mongoose does not strip `undefined` out of the filter, and MongoDB's null-equality semantics treat a genuinely missing field as matching it. Code that treats "the epoch is missing" as "matches anything" turns a fence into a no-op for precisely the rows the fence was supposed to protect. This is the general shape of adding a field to a system with rows already in it: the field's existence in the schema does not retroactively exist in every stored document, and anything that reads old rows has to decide, explicitly, what "missing" means — the disciplined version of that decision is the expand/contract migration pattern (add the column nullable, backfill every existing row, only then start relying on it as non-null) that [`../../../../sql-ledger/src/migrations/README.md`](../../../../sql-ledger/src/migrations/README.md) walks through for a schema change with money on the line. This toy skips the backfill step deliberately rather than by oversight: every `IdempotencyKey` document carries a 24-hour TTL regardless of its `epoch`, so any row written before this fix ages out of the collection within a day of the deploy, and the honest reason to skip a backfill here is that one, not that it wasn't needed in general.
- **Request deduplication is not business-intent deduplication.** This feature stops the *same request* from executing twice. It does nothing about a user who deliberately clicks "place order" twice in two browser tabs with two different keys — that is two different requests expressing the same underlying intent, and preventing it (if it should be prevented at all) is a product decision about duplicate orders, not a retry-safety problem. Conflating the two leads to systems that either block legitimate repeat purchases or fail to protect against a client bug that resends the same request forever.
- **The same idea, from the two other angles already in this monorepo.** `mern-tickets/server/src/hooks/README.md` argues idempotency from the *rejection* side — a pipeline that runs at most once and treats a resubmission as an error to reject rather than a request to replay — and is explicit that its own `duplicateContentHandler` is a content-dedup spam filter, not a real idempotency mechanism, because it has no key and no stored result. `mern-movies/server/src/notifications/README.md` shows the same unique-index-as-dedupe trick used here, but for making a fan-out handler safe to *re-run* rather than making an HTTP endpoint safe to *retry* — a natural composite key (`{ user, movie, actor }`) instead of a client-supplied one. All three are the same underlying idea — let the database's uniqueness guarantee answer "did this already happen?" — applied to three different problems.

## Standard practice

- Take a client-generated key and store the first result (status + body) under it, replaying it verbatim for every retry — Stripe's own description is the reference: "saving the resulting status code and body of the first request ... regardless of whether it succeeds or fails."
- Claim the key with a single atomic insert against a unique constraint, never a read-then-write — a check-then-insert has a race window where two concurrent requests both see "not claimed yet" and both proceed.
- Scope the key to the caller, not globally — an unscoped key namespace lets one client's guess collide with another client's stored response.
- Fingerprint the request body and reject a same-key-different-body request distinctly from a genuine retry — otherwise the key silently stops meaning what the client thinks it means.
- Respond immediately (409, not a wait) to a request whose duplicate is still in flight — waiting turns one slow request into two and takes the retry decision away from the caller.
- Prune keys after a bounded retention window with a TTL index or equivalent reaper — an idempotency store that never expires grows without bound and eventually becomes its own storage problem.
- Decide, and document, what happens to the claim on failure — this app releases the key on 5xx (network/server errors are exactly what a client should retry against a fresh attempt) and stores the response on 4xx (a deterministic client error — bad input, business rule violation — will fail identically on retry, so replaying it is both correct and cheaper than re-running the whole request).
- Give `in_progress` claims a lease, not just an eventual TTL — the TTL bounds how long an idempotency store grows, the lease bounds how long one crashed or failed request can block every retry, and they solve different problems on different timescales (30 seconds versus 24 hours here).
- Never ship a lease without a fencing token — a lease alone cannot tell "the holder is dead" from "the holder is just slow," and reclaiming from a merely-slow holder without a fence lets two owners believe they hold the same claim and corrupt shared state when both eventually write to it.
- Log a failed persistence write at error level with enough context to find it (the key, the user, the status) — a silent failure in the one code path meant to prevent double-execution is worse than most other silent failures in the system, because it looks identical to success from the outside. Log a fenced-out (superseded) write too, but as a warning, not an error — it is the fence working as designed, not a failure.
- Require the key on endpoints where a duplicate write has real cost (payments, order placement) rather than treating it as always-optional — see below for why this app does the opposite and what that costs.
- Prove atomicity with a sequential probe (claim, let it commit, claim again, expect the second to fail) in addition to a concurrent one — see the core concepts note above for why the concurrent test alone can pass against a genuinely broken implementation whenever a unique index sits underneath it.

## What this toy skips

- **The header is optional here, and a real payment API usually would not make it so.** `middleware/idempotency.js:10-13` lets a request with no `Idempotency-Key` through unchanged, meaning a client that forgets the header gets zero protection and a naive retry still creates a second order. Stripe and most production payment APIs make the header effectively mandatory on money-moving endpoints — some reject requests without one outright — precisely because "the client remembered to opt in" is not a safety property. This app makes it optional to keep the demo's existing tests (which predate this feature and don't send the header) working unchanged; a real deployment protecting an endpoint this sensitive should not offer that escape hatch.
- No idempotency key support on any endpoint besides order placement — cart mutations, for instance, have no equivalent protection.
- **The persistence contract lives in `res.json` and nowhere else.** The store-or-release write happens inside the monkey-patched `res.json` (`middleware/idempotency.js:53-73`), so a handler that answers through `res.send`, `res.sendStatus`, `res.end`, or a stream never stores its response and never releases its claim — the key stays `in_progress`, rides the 30-second lease into a reclaim, and the request re-executes even though the original completed fine. This app never hits the gap because the one guarded endpoint (and the error handler behind it) always responds via `res.json`, but the contract is implicit: wiring this middleware in front of any handler that responds another way silently downgrades "at most once" to "at most once per lease window."
- **The lease is measured across two clocks.** `claimedAt` is stamped by the process that wins the claim (the schema default at insert time, `models/idempotencyKey.js:10`), while `staleBefore` is computed from the clock of whichever process later reads it (`middleware/idempotency.js:39`). On one box that is one clock; across instances, skew stretches or shrinks the 30-second lease by exactly the skew — a fast-clocked reader reclaims early and duplicates more, a slow-clocked one reclaims late and wedges retries longer. The epoch fence keeps the store consistent either way; the lease *duration* is only as trustworthy as the fleet's clock sync.
- No enumeration of "concurrent request while claiming" beyond the duplicate-key path — a claim that fails for a reason other than `11000` (a genuine database outage, say) is passed to `next(err)` and surfaces as a 500 with no retry guidance specific to this feature.
- No backoff or jitter guidance in the `409` response beyond a flat `Retry-After: 1` — a real client-facing contract would likely want this tuned to the endpoint's typical latency.
- **The fencing token protects the idempotency store, not the downstream side effect.** Once a reclaim happens against a request that is still genuinely running (not dead, just slow), that request's handler keeps executing — this app has no mechanism to cancel it, and none to stop `orders.place()` from actually creating a second order. The epoch fence guarantees the *store* ends up consistent (one winning completed response, no accidental deletion of a live claim), not that the *operation* only happened once. A production system that needed to close this gap fully would have to thread the fencing token into the side-effecting write itself — the order-creation call would need to carry and check the epoch — which this app does not do.
- The lease timeout (30 seconds) is a single hardcoded default, not tuned per endpoint or measured against this app's actual latency distribution — the shorter this number, the more often a genuinely-slow-but-alive request gets reclaimed and duplicated per the point above; the longer it is, the longer a truly crashed request wedges retries. There is no value that eliminates both failure modes at once, only a tradeoff between them.
- The error and warning logs (`middleware/idempotency.js:61,66,70`) are `console.error`/`console.warn`, with no structured fields, no alerting, and no metric — an operator would have to be watching stdout at the right moment to notice a pattern of either kind.
- No admin visibility into stored idempotency records — there's no endpoint to inspect, list, or manually expire a key, which an operator debugging a stuck client would want.
- The fingerprint canonicalises key order and nested objects/arrays but has no defined behaviour for values whose JSON serialization is inherently unstable (e.g. `NaN`, `undefined` inside an array) — this app's request bodies don't exercise that edge, so it's untested here.

## In the real world (AWS / GCP)

- **No gateway does this for you.** API Gateway (AWS) and Cloud Endpoints/Apigee (GCP) can throttle, authenticate, and cache, but none of them implement Idempotency-Key claim/replay semantics for a mutating POST — the pattern in this README stays application code wherever you deploy. What changes is the claim store.
- **The claim store maps onto conditional writes.** This middleware's insert-against-a-unique-index becomes a **DynamoDB `PutItem` with `attribute_not_exists(pk)`** (AWS) or a **Firestore `create()`** (GCP) — both fail atomically if the key exists, which is the same first-insert-wins race resolution. The TTL index becomes DynamoDB TTL / Firestore TTL policies; the epoch fence stays a plain conditioned update in either.
- **AWS ships a reference implementation worth reading**: **Lambda Powertools' idempotency utility** is this exact middleware — key claim in DynamoDB, in-progress state with an expiry (their `in_progress_expiry` is this app's lease), stored response replay, payload-hash validation (this app's fingerprint). Comparing its design decisions against this README is a fast way to check you understood both.
- **Where the key comes from matters more at scale**: Stripe, Adyen, and most payment APIs require the header on money-moving endpoints; internally, event-driven consumers (SQS/Pub/Sub handlers) apply the same pattern with the message id as the key — that is the "inbox" side, and it is the same table shape with the broker supplying the key instead of the client.

## Try it

With the dev server running (`npm run dev`) and seed data loaded, log in and add something to a cart first — identity now comes from the access token, per `../session/README.md`, not from anything in the order body:

```bash
curl -s -X POST http://localhost:5000/api/auth/login -H 'Content-Type: application/json' -d '{"email":"demo@shop.test","password":"demo1234"}'
curl -s -X POST http://localhost:5000/api/cart/cart-1/items -H 'Content-Type: application/json' -d '{"productId":"<a seeded product id>","qty":1}'
```

Place an order with an idempotency key, using the `accessToken` from the login response:

```bash
curl -i -X POST http://localhost:5000/api/orders \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <accessToken>' \
  -H 'Idempotency-Key: demo-key-1' \
  -d '{"cartId":"cart-1","customer":{"name":"Ada","email":"ada@shop.test","address":"1 Main Street"}}'
```

Note the `_id` in the response, then repeat the exact same request:

```bash
curl -i -X POST http://localhost:5000/api/orders \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <accessToken>' \
  -H 'Idempotency-Key: demo-key-1' \
  -d '{"cartId":"cart-1","customer":{"name":"Ada","email":"ada@shop.test","address":"1 Main Street"}}'
```

The second response carries `Idempotent-Replay: true` and the identical `_id` — no second order was created. Now send the same key with a different body:

```bash
curl -i -X POST http://localhost:5000/api/orders \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <accessToken>' \
  -H 'Idempotency-Key: demo-key-1' \
  -d '{"cartId":"cart-1","customer":{"name":"Bea","email":"bea@shop.test","address":"1 Main Street"}}'
```

That returns `422`. Finally, fire two identical requests with a fresh key at the same instant to see the in-flight `409`. The first order above already emptied `cart-1`, so re-add an item before this step — skipping it makes both requests fail `400 cart is empty` instead of racing to create an order, since the cart check runs before the idempotency claim ever matters:

```bash
curl -s -X POST http://localhost:5000/api/cart/cart-1/items -H 'Content-Type: application/json' -d '{"productId":"<a seeded product id>","qty":1}'
curl -i -X POST http://localhost:5000/api/orders -H 'Content-Type: application/json' -H "Authorization: Bearer <accessToken>" -H 'Idempotency-Key: demo-key-2' -d '{"cartId":"cart-1","customer":{"name":"Ada","email":"ada@shop.test","address":"1 Main Street"}}' & \
curl -i -X POST http://localhost:5000/api/orders -H 'Content-Type: application/json' -H "Authorization: Bearer <accessToken>" -H 'Idempotency-Key: demo-key-2' -d '{"cartId":"cart-1","customer":{"name":"Ada","email":"ada@shop.test","address":"1 Main Street"}}'
```

One prints `201`, the other `409` with `Retry-After: 1` — whichever wins the race with the database.

## Further reading

- [Stripe API reference, Idempotent requests](https://docs.stripe.com/api/idempotent_requests) — the reference implementation this design follows: first result stored (success or failure), replayed on retry, parameter mismatch is an error, keys pruned after roughly 24 hours.
- [Brandur Leach, Implementing Stripe-like idempotency keys in Postgres](https://brandur.org/idempotency-keys) — the deepest public write-up of the mechanics: an atomic claim via a unique constraint, a recovery-point state machine for multi-step operations, and a reaper for expired keys. This app's claim/replay/release shape is a simplified version of the same idea.
- [draft-ietf-httpapi-idempotency-key-header](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) — the attempt to standardize the `Idempotency-Key` header. Worth reading with the caveat this README states plainly: the draft expired without becoming an RFC, so this is a widely copied vendor convention, not a standard.
- [RFC 9110 §9.2.2, Idempotent Methods](https://httpwg.org/specs/rfc9110.html#idempotent.methods) — the formal definition of "idempotent by nature," and the reason `POST` needs a bolted-on mechanism that `PUT`/`DELETE` get for free.
- [MongoDB: Unique Indexes](https://www.mongodb.com/docs/manual/core/index-unique/) — the exact guarantee the atomic claim rests on: "a unique compound index ensures that any given combination of the index key values appears at most once."
- [MongoDB: TTL Indexes](https://www.mongodb.com/docs/manual/core/index-ttl/) — the retention mechanism, including the roughly-60-second background sweep and the explicit statement that expiry is not instant deletion.
- [`../../../../mern-tickets/server/src/hooks/README.md`](../../../../mern-tickets/server/src/hooks/README.md) — the same concept from the rejection side: a pipeline that runs at most once and treats a resubmission as an error, plus an honest accounting of why its own content-dedup handler is not actually an idempotency mechanism.
- [`../../../../mern-movies/server/src/notifications/README.md`](../../../../mern-movies/server/src/notifications/README.md) — the same unique-index-as-dedupe trick used to make a fan-out handler safely re-runnable, with a natural composite key instead of a client-supplied one.
- [`../rateLimit/README.md`](../rateLimit/README.md) — the atomic-upsert pattern this feature's claim step is modelled on, and the sibling case (a shared counter) where the retry-after-duplicate-key-error path differs from this file's insert-and-fail-fast approach.
- [`../session/README.md`](../session/README.md) — why `userIdFrom` in `routes/orders.js:8` reads `req.userId` rather than `req.body.userId`, and what that consequence looked like in this app's tests.
