# Sagas and compensation

## What this is

The topic this app exists for. `POST /api/orders` is one business transaction — reserve inventory, charge payment, place the order, confirm shipping — but those four steps stand in for four *separate services*, each with its own database, and there is no single transaction that can span all of them. You cannot `BEGIN`, touch four services, and `COMMIT`; the moment a step commits in one service, it is durable there whether or not the next step ever succeeds. A **saga** is the answer to "how do I get a multi-service transaction to either finish or leave the world consistent, without a transaction that spans the services." It is a sequence of local transactions, one per service, where each step that can be undone has a **compensating action** that semantically reverses it — and the saga either runs all the forward steps to completion, or runs the compensations for the steps that already committed, in reverse. It does not give you atomicity or isolation across the services; it gives you a disciplined way to reach a consistent end state anyway. This app is the orchestrated variant: one coordinator drives the steps and owns the decision to go forward or roll back, and the whole decision is persisted so a crashed coordinator resumes instead of stranding a half-finished order.

The domain here is deliberately concrete. Four local tables — `inventory`/`reservations`, `payments`, `orders`, `shipments` — stand in for four services that in production would be behind network calls. `services/orders.js`'s `placeOrder` (`src/services/orders.js:14-35`) writes the order and the saga log in one real transaction, then hands the saga id to the orchestrator; every step after that is its own separate commit, exactly as it would be if each step were a remote call.

## How it works here

**The saga log is written first, in the same transaction as the order.** `placeOrder` opens one `withTransaction` (`src/db.js:8-25`) that inserts the `orders` row and then, via `startSaga` (`src/saga/engine.js:70-82`), the `saga` header row plus one `saga_steps` row per step in the definition (`src/saga/definitions.js`). That is the same trick the [transactional outbox](../../../sql-ledger/src/outbox/README.md) uses: the *intent* to run this saga (and the ordered list of steps, their kinds, and their retry budgets) is committed atomically with the business row it describes, so there is never an order without a saga log or a saga log without an order. Only after that transaction commits does `placeOrder` call `runSaga` on the pool — outside any enclosing transaction, because each step must be free to commit on its own.

**The orchestrator runs steps forward, one at a time.** `runSaga` (`src/saga/engine.js:39-68`) loads the saga and its steps ordered by `position`, then walks them. A step already marked `done` is skipped (and, if it was compensatable, remembered on the `compensatableDone` stack so a later abort can still undo it) — that skip is the whole of crash-resume: because every completed step's status is persisted, a coordinator that died mid-saga and is re-invoked on the same `sagaId` picks up at the first not-yet-`done` step and never re-runs the ones that already committed. `test/saga.test.js`'s resume test proves exactly this by marking a step `done` out of band and asserting its action never fires on the next run.

**Each step gets a retry budget with backoff before it is treated as failed.** `runStepWithRetry` (`src/saga/engine.js:8-26`) calls the step's `action`, and on a throw records the attempt and its error message on the `saga_steps` row (`recordAttempt`), then either retries after `backoffMs(attempt, ...)` (`src/saga/backoff.js` — the same full-jitter `random() * min(cap, base * 2 ** attempts)` shape as the [outbox](../../../sql-ledger/src/outbox/README.md) and [queue](../../../sql-jobs/src/queue/README.md)) or, once `attempts` reaches the step's `max_attempts`, marks the step `failed` and returns. A flaky step that recovers within its budget is a normal success; only budget exhaustion counts as a step failure.

**A compensatable step's failure aborts the saga; a post-pivot failure does not.** This is the centre of the whole design and lives in six lines (`src/saga/engine.js:59-64`). When `runStepWithRetry` reports a permanent failure, the orchestrator branches on the step's `kind`:

- if the failed step is **compensatable**, it calls `compensate` (`src/saga/engine.js:28-37`), which walks the `compensatableDone` stack *in reverse* — undoing the most recently completed step first — invoking each step's `compensate` action and marking the step `compensated`, then sets the saga `compensated`. The saga aborted cleanly: everything that had committed has been semantically undone.
- if the failed step is the **pivot** or a **retryable** step (everything from the pivot onward), there is nothing to abort back to — the saga has passed the point of no return — so it sets the saga `failed` and stops, without touching any prior step. `test/saga.test.js`'s "past the pivot" test asserts that a permanently-failing retryable step leaves the earlier compensatable steps `done`, not `compensated`, and the saga `failed`, not `compensated`.

**Steps and compensations are idempotent, because execution is at-least-once.** Each domain action is keyed on the `sagaId` so that running it twice is a no-op the second time: `inventoryRepo.reserve` (`src/repositories/inventory.js`) inserts the reservation `ON CONFLICT (saga_id, sku) DO NOTHING` and only decrements stock for a row it actually inserted, so a replay reserves nothing again; `release` flips a `released` flag and only restores stock while the flag was still false; `paymentsRepo.charge` inserts `ON CONFLICT (saga_id) DO NOTHING`; `shipmentsRepo.schedule` the same. This matters for the same reason it matters in the [queue](../../../sql-jobs/src/queue/README.md) and [idempotency](../../../mern-shop/server/src/idempotency/README.md) guides: a crashed-and-resumed orchestrator, or a compensation that runs after a forward step that had already partly succeeded, will re-issue calls, and the only thing that makes that safe is the receiver treating a replay as a no-op. `test/saga.test.js`'s idempotency test drives reserve/release/charge twice each and asserts stock moved once and exactly one payment row exists.

## The core concepts

- **Orchestration versus choreography, and why this app orchestrates.** There are two ways to run a saga. In **choreography** there is no coordinator: each service reacts to the previous service's event and emits its own ("payment charged" → shipping hears it and ships), so the saga's logic is smeared across every participant and the control flow exists only as an emergent property of who subscribes to what. In **orchestration** a single coordinator holds the sequence and tells each service what to do next, collecting the result. Choreography is more decoupled and has no central bottleneck, but the flow is genuinely hard to see, reason about, or change — no one object knows the whole saga — and detecting that a saga is stuck is its own distributed problem. Orchestration centralises the logic (easier to understand, test, and modify, and the coordinator is the obvious place to see and drive a stuck saga) at the cost of a component every step depends on. This app chose orchestration precisely because the *point* is to make the pivot/compensate decision legible: it is six lines in one function (`src/saga/engine.js:59-64`) you can read top to bottom, which is impossible to achieve when the same decision is an emergent consequence of a dozen event subscriptions. The standard warning against orchestration — don't let the orchestrator absorb business logic that belongs in the services — still applies: here the orchestrator only sequences and decides forward-or-back; every actual effect lives in a domain repository the step calls.
- **The saga log is the whole reliability story.** A saga with no durable record of where it is cannot survive a coordinator crash — on restart it has no idea which steps committed, so it cannot know whether to go forward or compensate, and re-running from the top double-charges. The `saga` + `saga_steps` rows are that record: written in the same transaction as the business row (durable intent, exactly the outbox lesson), updated to `done`/`failed`/`compensated` as each step settles, so the state needed to resume or to compensate is always on disk, never only in the coordinator's memory. Persisting the *step kind* and the *compensation data* (here, the saga `context` — `sku`, `qty`, `amount`, `address`, `orderId`) alongside each step is what lets a fresh process, with none of the original request's variables in scope, still run the right compensations.
- **A saga is ACD, not ACID — it has no isolation, and that is the hard part.** The database gives a single local transaction Atomicity, Consistency, Isolation, Durability. A saga gives you Atomicity (all-or-nothing, via compensation), Consistency, and Durability — but **not Isolation**. Between the moment step 1 commits and the moment the saga finishes (or compensates), the partial results of the saga are *visible* to everyone else: the money is already charged, the stock already reserved, the order still `pending`. Another transaction reading in that window sees a state that may still be rolled back — a **dirty read** — and can make decisions on it (ship against a reservation that is about to be released) or overwrite a field the saga is about to compensate — a **lost update**. This is not a bug in this implementation; it is the defining limitation of the entire pattern, the price of not holding locks across services. Naming it precisely: sagas are ACD, and the missing I is a problem you must design around at the application level, because no amount of retry or compensation logic recovers it for you.
- **The countermeasures for the missing isolation — semantic locks, commutative updates, by-value vs by-reference.** The saga literature (Garcia-Molina & Salem originally, Richardson's *Microservices Patterns* in modern form) gives a toolbox for the isolation you gave up. A **semantic lock** is an application-level flag on the record a saga is touching — an order left in a `pending`/`PENDING_PAYMENT` state that says "a saga owns this, treat it as not-yet-final" — so other transactions can *see* the lock and refuse to act on the record until the saga clears it; this app's `orders.status = 'pending'` until the pivot flips it to `placed` is exactly a semantic lock. **Commutative updates** sidestep lost updates by making the operations order-independent: model money movement as `credit`/`debit` deltas rather than "set balance to X", and a compensation that credits back commutes with any concurrent debit instead of clobbering it — the [ledger](../../../sql-ledger/src/ledger/README.md)'s append-only entries are the same idea. **By-value versus by-reference** is a choice about what the compensation reads: *by-reference* compensation re-reads current state and acts on it (fragile — the state may have moved under a dirty read), while *by-value* compensation carries the exact data it needs to undo the step, captured at the time the step ran, in the saga log itself. This app compensates by value: `release` and `refund` work from the `saga_id`-keyed rows and the persisted `context`, never from a fresh read of "what does the world look like now," which is what makes them safe to run late and safe to run twice.
- **The step taxonomy: compensatable, pivot, retryable — and why the pivot is the point of no return.** Richardson's taxonomy splits a saga's steps into three kinds around a single hinge. **Compensatable transactions** are the steps that can still be undone, so a failure anywhere among them (or after them, before the pivot) can abort the whole saga by compensating backward — `reserve_inventory` and `charge_payment` here. The **pivot transaction** is the go/no-go point: once it commits, the saga is committed to running to completion and will never be compensated. **Retryable transactions** follow the pivot and are the steps that *must* eventually succeed — they are designed so that retrying is always safe and, given enough retries, they will complete; they are never compensated, only retried. `confirm_shipping` is retryable: if the carrier's API is down, you retry, you do not un-charge the customer for an order they have already paid for and that the warehouse is already committed to. The reason the pivot exists as a named concept is that it is where the saga's *failure semantics invert*: before it, "something went wrong" means "give everything back"; after it, "something went wrong" means "keep trying until it goes right." Encoding that inversion as data on each step (`kind`) rather than as scattered `if`s is what keeps the orchestrator's decision to six readable lines.
- **Why two-phase commit is avoided.** The textbook alternative to a saga is a distributed transaction via **two-phase commit (2PC)**: a coordinator asks every participant to *prepare* (do the work, promise you can commit, hold your locks), and once all have voted yes, tells them all to *commit*. It genuinely gives you atomicity and isolation across services — the thing a saga cannot. It is avoided anyway for two reasons that matter more at scale than the guarantee it buys. First, it is **blocking**: every participant holds its locks from prepare until the final commit/abort arrives, so a slow or crashed participant — or a crashed *coordinator* after everyone prepared — leaves the others pinned, unable to release locks or make progress, sometimes indefinitely (the coordinator is a single point of failure at exactly the worst moment). Second, that lock-holding across a network round trip is a direct **availability and throughput cost**: you have coupled the availability of the whole transaction to the availability of its least-available participant, which is the opposite of what a service-oriented architecture is trying to buy. Many modern data stores and message brokers do not even offer the XA/2PC hooks a distributed transaction needs. A saga trades away isolation (the ACD-not-ACID cost above) specifically to get non-blocking, per-service commits back — each step commits and releases its locks immediately, and no participant ever waits on another's lock. That is the trade: 2PC keeps isolation and pays with blocking and availability; sagas keep availability and pay with the missing I.

## Standard practice

- Persist the saga log in the same transaction as the business write it drives, and update it as each step settles — a saga whose state lives only in the coordinator's memory cannot survive the coordinator, and cannot be resumed or audited.
- Make every step and every compensation idempotent, keyed on the saga id (or another stable natural key), because a resumed or retried saga re-issues calls at least once — the same conclusion the [queue](../../../sql-jobs/src/queue/README.md) and [idempotency](../../../mern-shop/server/src/idempotency/README.md) guides reach from their own directions.
- Compensate in the reverse of the order steps completed, so each undo runs against the state its forward step left behind — verified here by a test that asserts the compensation order is `['b','a']` after `a` then `b` committed, and confirmed load-bearing by mutating the loop to run forward and watching that test go red.
- Classify every step as compensatable, pivot, or retryable up front, and let the pivot's position decide failure semantics — never compensate a step that ran after the pivot, and never leave a post-pivot step un-retried. The pivot-guard in `runSaga` was mutated out (making every failure compensate) to confirm the "past the pivot" test catches it.
- Design compensations to work by value from data captured when the forward step ran, not by re-reading current state — a dirty read from a concurrent saga makes by-reference compensation unsound.
- Reach for a saga, not two-phase commit, when a transaction spans services that commit independently — accept the loss of isolation and cover it with semantic locks and commutative updates rather than paying 2PC's blocking cost.

## What this toy skips

- **No cross-service transport at all.** The four "services" are four tables in one Postgres, and every step is a direct function call inside one process. There is no network between steps, so there are no partial-failure modes that a real orchestrator must handle — a request that timed out but actually succeeded, a service that is unreachable versus one that rejected the call, an at-least-once *message* to a participant. The idempotency this app builds is the right shape for those modes, but it is never actually exercised against them here.
- **The orchestrator runs inline and synchronously inside the request.** `placeOrder` awaits the entire saga — including its backoff sleeps — before responding, so a saga that retries for real seconds blocks the HTTP request for real seconds. A production orchestrator drives steps off a durable queue (each step transition is a job), so the request returns immediately with a saga id and the work continues in the background; that is exactly the [queue](../../../sql-jobs/src/queue/README.md) this repo already builds, and wiring the engine onto it (one job per step transition, the saga log as the queue's business state) is the honest next step this toy does not take.
- **No isolation guarantee, and only the thinnest semantic lock.** The `orders.status = 'pending'` flag is a semantic lock in name, but nothing in this app actually *checks* it before reading or writing an in-flight order — a concurrent reader here would happily dirty-read a charged-but-not-committed saga. The countermeasures are described in the core concepts; only the by-value compensation is genuinely implemented.
- **Compensations cannot themselves fail.** The engine invokes `compensate` without a retry budget or a failure path (`src/saga/engine.js:28-37`); a compensation that threw would abort the whole `runSaga` call and leave the saga stuck `compensating`. Real compensations are themselves retryable transactions (they must eventually succeed, just like post-pivot steps) and need their own budget and their own idempotency — which the domain compensations here have, but the engine does not drive.
- **A post-pivot step that exhausts its budget just parks the saga as `failed`.** There is no operator surface to inspect or hand-drive a forward-stuck saga, and no alerting on sagas sitting in `compensating`/`failed` — the two states an operator would most want paged on. `GET /api/sagas/:id` shows the log, but nothing lists or escalates the stuck ones.
- **No timeout on a saga as a whole**, only per-step retry budgets. A saga that makes slow forward progress forever is never abandoned.

## In the real world (AWS / GCP)

The hand-rolled orchestrator here is the part you almost never build yourself in production — a managed workflow engine owns the state machine, the retries, and the catch-and-compensate wiring, and you supply only the step logic and the compensations.

- **AWS Step Functions is the orchestrator this engine imitates.** A Step Functions state machine *is* the saga definition: each state is a step, `Retry` on a state is the per-step retry budget with backoff (it even has jitter), and `Catch` is the transition that fires the compensating states in reverse. AWS documents this directly as the way to implement the saga pattern — the [Saga pattern with Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/tutorial-saga-pattern.html) reference is a compensating-transaction state machine, and their [saga sample](https://github.com/aws-samples/aws-step-functions-long-lived-transactions) is a reserve/charge/ship flow much like this one. The state machine's execution history is the durable saga log; you do not write `saga_steps`. **Temporal** (self-hosted or Temporal Cloud, workers on ECS/EKS) is the other common choice: the saga is ordinary code, Temporal persists every step's result as a durable event history and replays it to resume after a crash, and its SDK has a first-class saga/compensation helper — you register compensations as you go and it runs them in reverse on failure.
- **On GCP the same role is Workflows or Temporal on GKE.** **Google Cloud Workflows** is the declarative state-machine equivalent of Step Functions — steps, retries, and a `try`/`except` that runs compensation steps — and is the standard managed saga orchestrator on GCP. For a code-first engine you run **Temporal on GKE** (or Cadence), same model as above. **Cloud Composer** (managed Airflow) is the heavier, batch-flavoured option when the saga is really a data-pipeline DAG with compensation tasks rather than a per-request transaction.
- **What stays your code no matter which you buy: the compensations, and their idempotency.** The managed engine sequences steps and decides forward-or-back, but *what it means to release a reservation or refund a charge* is domain logic only your service knows — exactly the `compensate` functions in `src/saga/steps.js`. And because every one of these engines drives steps with at-least-once semantics (Step Functions can invoke a task more than once, Temporal replays, Workflows retries), the receiver-side idempotency this app keys on `saga_id` is not optional there either; it is the same portable guarantee the [outbox](../../../sql-ledger/src/outbox/README.md) and [queue](../../../sql-jobs/src/queue/README.md) READMEs carry into their managed equivalents.
- **The alternative you are deciding against stays 2PC.** Where a true distributed transaction is unavoidable, AWS and GCP both point you at a single strongly-consistent store that gives you a local transaction across what would otherwise be separate services — DynamoDB transactions, Aurora, Spanner — rather than a cross-service 2PC coordinator. The saga exists for the cases where that consolidation is not possible.

## Try it

Requires the app migrated (`npm run migrate`) and running (`npm run dev`). Seed some stock, place an order that succeeds, then one that cannot reserve and watch it abort:

```bash
curl -s -X POST http://localhost:5008/api/inventory -H 'Content-Type: application/json' -d '{"sku":"WIDGET-1","available":10}'
curl -s -X POST http://localhost:5008/api/orders -H 'Content-Type: application/json' -d '{"sku":"WIDGET-1","qty":2,"amountMinor":4999,"address":"1 Test Lane"}'
```

The response's `saga.status` is `completed`, every `steps[].status` is `done`, and `GET /api/inventory/WIDGET-1` now shows `available: 8, reserved: 2`, with a `payments` row and a `shipments` row for the saga. Now force an abort — order more than exists:

```bash
curl -s -X POST http://localhost:5008/api/inventory -H 'Content-Type: application/json' -d '{"sku":"WIDGET-SCARCE","available":1}'
curl -s -X POST http://localhost:5008/api/orders -H 'Content-Type: application/json' -d '{"sku":"WIDGET-SCARCE","qty":5,"amountMinor":9999,"address":"2 Test Lane"}'
```

`reserve_inventory` fails its whole retry budget (the stock never appears), so the saga ends `compensated`: no payment is taken, the order stays `pending`, and inventory is untouched. `npm run seed` sets up exactly these two sagas in one shot.

- [Hector Garcia-Molina & Kenneth Salem — Sagas (1987)](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf) — the original paper that named the pattern, for the long-lived-transaction motivation and the compensating-transaction definition everything since builds on.
- [Caitie McCaffrey — Applying the Saga Pattern (GOTO 2015)](https://www.youtube.com/watch?v=xDuwrtwYHu8) — the talk that reintroduced sagas to the microservices era; especially good on why isolation is the thing you actually lose and what to do about it.
- [AWS — Implement the saga pattern with Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/tutorial-saga-pattern.html) — the managed orchestrator this engine imitates, with `Retry`/`Catch` doing the retry-budget and compensate-on-failure work `runSaga` does by hand.
- [Temporal — Saga pattern](https://docs.temporal.io/encyclopedia/application-message-passing/saga) — the code-first orchestrator: compensations registered as you go, run in reverse on failure, with the durable event history that makes crash-resume automatic.
- [Microsoft — Two-phase commit and the case against distributed transactions](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga) — a clear statement of why 2PC's blocking coordinator and availability cost push service architectures toward sagas, framed as the same trade this README's core concepts describe.
